= Roc syntax parser: preliminary research

Research date: 2026-10-16. Scope: current Zig compiler syntax only.
Legacy Rust compiler syntax is out of scope.

This note supports planning a pure Roc syntax parser for highlighting and
future linting. The recommendations below are proposals, not implemented APIs
or measured performance claims. Three research agents investigated reference
parsers, the feedback harness, and parser architecture. No parser or harness
implementation was added as part of this research.

== Recommended direction

Use a pinned Roc compiler tokenizer/parser as the primary syntax reference.
Keep robustness and structured-generation properties inside native roc-fuzz
targets, written in Roc. Run differential comparisons through persistent worker
processes supervised by Python. Add Tree-sitter as a secondary editor-oriented
reference after checking its agreement with the compiler.

Build a lossless token stream and a flat syntax tree with source spans. Preserve
comments, whitespace, malformed text and incomplete constructs. Derive typed
AST views and contextual highlighting from that representation as coverage grows.

|Same grammar without the JS/WASM execution boundary; persistent native worker

The researched grammar is
https://github.com/faldor20/tree-sitter-roc/tree/7f9ae855ba7819c5d9279853691fd072e233226b[tree-sitter-roc
at 7f9ae855ba7819c5d9279853691fd072e233226b], committed 2026-10-15.
It supports current syntax features such as parenthesized calls, pipe-delimited
lambdas, `match` and nominal types; it should not be dismissed as legacy-only.
It also retains historical forms, so its acceptance alone cannot establish
agreement with the Zig compiler's syntax.
Its latest change supports `expect` inside blocks. This revision postdates the
compiler pin, so apparent disagreements may reflect syntax-version differences.
Pin the grammar, generated parser, runtime/CLI and WASM artifact hash together.
The grammar currently declares tree-sitter-cli 0.25.10 in its package metadata.
For that version, `tree-sitter build --wasm` needs Emscripten or container tooling;
the automatic wasi-sdk setup documented for 0.26.1 must not be assumed.
See the
https://github.com/tree-sitter/tree-sitter/blob/v0.25.10/lib/binding_web/README.md[versioned
WASM instructions]. No WASM artifact was built during this research.

The
https://github.com/tree-sitter/tree-sitter/tree/master/lib/binding_web[official
Web Tree-sitter documentation] describes loading runtime and language WASM
modules once and reusing a parser. Explicitly release trees between cases.
Normalize binding-specific string indices to UTF-8 byte offsets; test non-ASCII
text rather than assuming JavaScript indices equal native Tree-sitter bytes.

=== Compiler integration

At the pinned compiler revision,
https://github.com/roc-lang/roc/blob/7f11a825fb2df7fd48edb11e8c593ffdad4fcdb5/src/parse/mod.zig[parse/mod.zig]
exports file, expression, header, statement and top-level-statement entry points.
The basic ownership sequence is:

[source,zig]
----
var env = try base.CommonEnv.init(allocator, source);
defer env.deinit(allocator);
const ast = try parse.file(allocator, &env);
defer ast.deinit();
const has_errors = ast.hasErrors();
----

This call sequence was checked in source; a standalone adapter was not built.
Syntax errors return an AST with diagnostics; allocator failure is a separate
error path. For expression probes, verify complete token consumption explicitly.
Read tokenization and parsing diagnostics, not just the Zig function's success.
Avoid pretty S-expression generation in the hot loop; export a small normalized
projection and request detailed dumps only for failures.

The upstream build exports a module named `parse`, so `.zon` integration is
plausible. However, invoking the upstream build also configures dependencies
such as zstd and bytebox. Its `.zon` package paths omit vendor directories that
the full build graph references. A direct `dependency.module("parse")` needs
an actual build experiment before it can be relied on.

The more predictable first spike is a pinned full source checkout/archive and
a small build adapter wiring `parse`, `base`, `collections`, `reporting`,
`builtins`, `tracy` and build options. Disable Tracy. The parse-only path should
avoid LLVM linking; confirm this with a clean build and report dependency size,
build time and any required upstream changes. Zig 0.16.0 is the pin's declared
minimum; lock the tested toolchain exactly after this experiment.

The compiler tokenizer already exposes broad highlight categories. Its tokens
do not preserve whitespace/comments, so they cannot alone serve as our lossless
result. Token identity also depends on spacing: opening parentheses, dotted
names and unary/binary minus have context-sensitive distinctions. String
interpolation and escape handling require dedicated states.

== Harness design

=== Pure Roc inner loop

Use `Fuzz.raw_bytes` and `Fuzz.target_with!` for direct source corpora, following
`../../fuzz/markdown-document.roc`. Decide explicitly whether the public API
accepts arbitrary bytes or only valid `Str`; never silently turn invalid UTF-8
into an empty input in tests. A byte API can retain invalid bytes with diagnostics.

Use native `roc build --opt=speed --fuzz`. The pinned compiler requires the
LLVM backend for fuzz builds; this instruments compiled Roc code for coverage
feedback. Keep normal runtime benchmarks free of fuzz instrumentation.
See the
https://github.com/lukewilliamboswell/roc-fuzz/blob/b37bb7dc0b6aa44390d4bfa84978404e94cec885/platform/Fuzz.roc[pinned
Fuzz API] and
https://github.com/lukewilliamboswell/roc-fuzz/blob/b37bb7dc0b6aa44390d4bfa84978404e94cec885/docs/campaigns.adoc[campaign guide].

Start with two targets:

* Raw input: termination, determinism, valid spans/indices, token reconstruction,
  recovery progress and valid tree traversal. Malformed source is expected;
  returning diagnostics is not a fuzz failure.
* Structured generation: independently construct expected structure and render
  current Roc syntax, then compare the parser's normalized structure. Bound
  rendered bytes, nodes and nesting independently of generator entropy size.

Add syntax-aware metamorphic transformations. Arbitrary whitespace insertion
is unsafe because it can change Roc tokenization. Promote minimized failures
to reviewed regression fixtures and raw seeds. A random seed alone does not
reproduce a run across changing generators and corpora.

=== Differential outer loop

Python should build once, start one Roc probe and one reference worker, and
stream thousands of requests through them. Existing reviews sometimes launch a
probe per document; avoid copying that pattern for this harness.

Begin with versioned JSON Lines carrying case ID, parse mode and base64 source
bytes. Escaping/base64 preserves multiline documents and invalid UTF-8. Each
worker returns one response per request; stdout is protocol-only. Include status,
token kinds/spans and selected node kinds/relationships. Add source hashes and
tool identities to run metadata. A length-prefixed binary protocol is a later
option if serialization proves material.

Compare a deliberately small common projection. Initially compare token kinds
and byte spans, then supported syntax structure and syntax diagnostics.
Acceptance equality alone cannot detect precedence/associativity bugs.
Do not demand identical recovery trees, diagnostic messages or internal node IDs.
Distinguish unsupported implementation coverage, malformed syntax, resource limits,
oracle crashes and genuine mismatches. Check parser errors separately from
name-resolution/type errors: syntactically valid Roc need not typecheck.

Reset per-document allocator state, bound request sizes and execution time,
and persist the triggering request before restarting a failed worker. Validate
worker identity before reusing cached builds. Check structured generators against
the compiler before trusting their generated source as valid.

== Proposed representation and performance constraints

Use half-open UTF-8 byte spans `{ start, end }`, one retained source buffer,
flat token/node/child-index buffers, structured diagnostic codes, and a result
status distinguishing complete, recovered, unsupported and limited parses.
Preserve all source bytes with trivia tokens or explicit gaps. A small public
view API can hide storage choices while supporting future typed AST views.
Resource exhaustion should return a documented limit result where possible;
it must not be reported as an ordinary syntax mismatch.

* Scan bytes forward and parse tokens with bounded lookahead. Use an explicit
  work stack for nesting and recovery. Every recovery step consumes input or
  reduces pending work.
* Keep growing buffers uniquely owned. The existing Markdown scanner documents
  repeated copies when a growing list is retained inside another record/stack.
  Avoid recursive subtree construction with repeated concatenation.
* Store spans instead of allocating identifier/literal strings. Format diagnostics
  outside the parse loop. Build a line-start index once when needed; convert
  byte offsets to editor/LSP coordinates at the boundary.
* Derive precedence and whitespace-sensitive rules from the pinned compiler,
  with fixtures for associativity, calls, field access, unary/binary operators,
  patterns, type annotations, interpolation and multiline constructs.
* Set explicit nesting, diagnostic and output budgets. Recovery must preserve
  later valid declarations when possible. A tolerant tree can coexist with
  strict validity checks for complete supported source.
* Start with full-document parsing. Incremental parsing is a later design
  decision informed by measured editor-size latency; it is not provided merely
  by choosing a flat tree.

Reuse `../../scripts/bench.py`, `../../bench/roc/Bench.roc` and
`../../bench/roc/alloc.roc`, extending their format registries when ready.
Measure lexing, tree construction, highlighting and serialization separately.
Report cold startup separately from warm throughput, cases/s for tiny inputs,
latency and bytes/s for documents, and retained-result memory.

Use 1x/2x/4x/8x families for long operator chains, deep nesting, many siblings,
large strings/comments, repeated ambiguous prefixes and malformed recovery.
Wall-clock scaling is evidence, not a proof of linear complexity; deterministic
work counters can strengthen the check. Establish baselines before setting
absolute performance budgets.

`Fuzz.measure_allocs!` counts allocation/reallocation calls, not allocated bytes
or peak memory. Whole-process RSS includes runtime/corpus overhead. Test input
sharing as well as unique ownership, since Roc reference counting affects copies.
Bounded allocation counts alone cannot detect large repeated reallocations.

== First implementation milestone

. Pin the compiler source/toolchain, protocol and corpus manifest. Prove a
  parse-only Zig worker builds, handles multiple cases and releases state.
. Add an internal Roc syntax module with source/span/token/result types and a
  lossless scanner. Grow lexical coverage explicitly; mark remaining syntax
  unsupported rather than claiming it is invalid.
. Parse identifiers, literals, parentheses, calls, binary expressions and simple
  declarations. Use expression mode before expanding file/header grammar.
. Connect a persistent Roc probe and compare a small pinned corpus, including
  grouping, precedence, Unicode, comments, incomplete source and later-declaration
  recovery. Expose lexical highlight spans in the probe output.
. Add raw and structured fuzz targets, seed/dictionary files, registration in
  `run_fuzz.py`, matching workflow entries, replay and regression promotion.
. Record optimized runtime and allocation baselines, then expand grammar coverage.

The milestone is complete when multiple documents flow through both workers,
supported fixtures agree structurally, malformed inputs retain useful spans,
raw and structured fuzz smoke runs pass, a deliberately injected mismatch is
detected and replayable, and timing/allocation baselines are recorded.
No throughput target or standalone compiler integration has yet been validated.

The repository's existing module, conformance, fuzz-registration and documentation
checks apply as implementation grows. A future public API should be documented
and agreed before release; this research does not commit to a public module name.

== Reference drift audit, 16 October 2026

A source audit compared the original syntax reference,
`7f11a825fb2df7fd48edb11e8c593ffdad4fcdb5` (29 September), the installed
implementation compiler source `38e6c42c889cc7ffd97beea9199186790cc848f5`
(15 October), and the newer oracle reference
`0d4b0ab02f9239448d034db17b4e63051a7c57ae`. Each revision was fetched into
an isolated bare cache; the sibling compiler working tree was not changed.
The implementation compiler remains the installed October nightly.

The nine inventoried AST union categories retain the same 107 variants, but
acceptance changed. October permits an ellipsis to start a new expression after
a preceding expression, and distinguishes unary `-...` from subtraction after
an expression. It adds a specific diagnostic for `=` used as a record field
separator and changes record/block lookahead. Tokenization rejects literal
bidirectional controls in every lexical context, diagnoses a leading UTF-8 BOM,
and preserves failure independently of diagnostic-buffer capacity. Escaped
Unicode values and a BOM inside a literal remain distinct from source controls.

The newer main reference additionally checks dependency records in app, package
and platform headers. Duplicate shorthands, punned or non-string sources,
interpolated sources and sources containing backslash escapes are rejected.
These are real acceptance differences; a green September corpus cannot establish
conformance to the newer grammar.

The compiler internals changed generic NodeStore collections, region storage,
type extensions and Zig integer conversions, but the adapter reads through
compatible public AST getters. A native compatibility build with Zig 0.17
succeeded without changing its AST projection schemas. The worker must honor
the newer tokenizer failure flags. Zig 0.17 removes the
`zig build --global-cache-dir` option; the build helper must supply
`ZIG_GLOBAL_CACHE_DIR` instead. The audit established source differences
and adapter requirements, not new runtime or allocation measurements. Historical
results above retain their original reference and measurement scope.
