[#property-testing]
= Property tests and conformance reviews
:idprefix: _
:idseparator: _

This chapter is for contributors who change a parser and need to know whether
the change is correct. The first half explains how roc-parser checks its
parsers beyond the `expect` tests: property tests driven by a fuzzer, and
reviews against a mature reference implementation. The second half is a set of
how-to sections: run the targets, reproduce and minimise a failure, turn it
into a regression, and update a conformance baseline.

It assumes the setup in <<contributing>>, including the latest Roc nightly,
which CI uses too. Every command below uses that compiler:

[source,bash]
----
export ROC=/path/to/roc_nightly/roc
----

== Why property tests

An `expect` test checks one input that somebody thought of. Parsers fail on the
inputs nobody thought of: a carriage return on its own, a quote in the middle
of a field, 100,000 nested brackets. A property test states something that must
hold for _every_ input, and a fuzzer searches for an input where it does not.

The fuzzer is https://github.com/lukewilliamboswell/roc-fuzz[roc-fuzz], a Roc
platform that embeds libFuzzer. It is coverage guided: it keeps inputs that
reach new code and mutates them further, so it finds deep paths far faster than
random input would. The targets are library quality tests, not a security
programme. The established targets run on pull requests and nightly in CI.
The HTML/SVG/MathML targets are local-only: `smoke all` includes them, while
CI uses `smoke --ci all` and the scheduled matrix excludes them.

A failing property is a bug in the parser, or occasionally in the property.
Either way the outcome is a fix: see <<property-testing-fix-the-cause>>.

Keep the committed seeds small. A generator should describe a class of inputs
and a property should check its contract across sizes and variations. Prefer
round trips, independent models, metamorphic relations and resource bounds to
large lists of prescribed input/output pairs. Shrink failures and keep a small
explicit regression witness when it explains a contract the generator would
otherwise miss.

Expanded corpora, timing samples and comparison scaffolds belong in ignored
`.roc-parser-tmp/` storage. Generate scaling documents from parameters. Recreate
external suites from pinned revisions with verified hashes, retaining the
acquisition recipe and pins in Git. Replacing a dataset must preserve its useful
checks; moving assertions out of the repository is not a substitute for them.

== Three kinds of target

Each `fuzz/*Property.roc` module owns one property. Seven `*Properties.roc`
applications group the scheduled properties into shared executables. Markup
and diagnostic investigations have separate local executables. Each property
retains its name, examples, corpus and reports; selection happens through the
executable's `--target` option rather than a byte added to the input.

CSV retention uses its own `CsvRetention` executable while
https://github.com/roc-lang/roc/issues/13191[the compiler's hosted-box row-join bug]
affects combined suites. It keeps the same backend, opaque measurement ownership
fence, diagnostic assertions and allocation ceilings.

Properties come in three kinds, which differ in what the fuzzer's bytes mean
and therefore in what the property can check.

Raw targets (`xml-raw`, `xml-reader`, `xml-limits`, `xmlns-raw`, `yaml-raw`,
`yaml-source`, `json-raw`, `json-options`, `csv-raw`, `http-raw`,
`markdown-inline`, `markdown-document`, `string-primitives`):: The bytes are the input document,
often invalid UTF-8. Nothing is known about the expected result, so the target
checks properties that hold for any document: the parser does not crash or
hang, an error points inside the input, LF/CRLF/CR line endings give the same
result, appending a final line break changes nothing, and the result survives
re-serialisation. These are called _metamorphic relations_: they relate two
runs of the parser instead of comparing one run with a known answer. Many raw
targets also switch to a pathological generator (deep nesting, thousands of
attributes, long delimiter runs) when the input starts with a marker byte, so
that the per-input `--timeout` catches quadratic behaviour.

The XML pull reader and namespaces have their own raw targets:

* `xml-reader` requires `Xml.reader`'s events to build `Xml.parse_str`'s tree,
  or to fail with its error; `Reader.element` at a start chosen from the input
  to build that subtree, with the following events unchanged; and every tag
  event to be located at a `<`.
* `xml-limits` uses its first three bytes to choose low `Xml.ReaderProps`
  limits. A document within them parses to `parse_str`'s tree, one past them
  fails with a `LimitExceeded` it really exceeds, located no later than any
  well-formedness error, and the parse holds no more than a ceiling linear in
  the input and in `max_elements`.
* `xmlns-raw` requires `Xml.Namespaced` to agree with `Xml` on well-formedness, to give
  a tree of `Xml`'s shape whose names resolve as an independent walk of the
  bindings says, and to write trees that read back the same, with their own
  prefixes and with a table of fresh ones.

`xml-ceilings` is a measuring target: two bytes choose a document shape and
size, and `Fuzz.measure!` requires the allocator traffic and held bytes of
`Xml.parse_str`, a loop over `Xml.Reader.next` and `Xml.Namespaced.parse_str` to stay
under ceilings linear in the document (and, for the reader, in its depth). Its
22 declared examples are a small and a large document of each shape, and its
whole input space is a few thousand documents. Ceilings only move down; a
pull request that raises one states why.

The `yaml-source` target checks the highlighting API separately from semantic
parsing: token spans partition every original byte, diagnostics stay in range,
key categories agree with roles, and repeated tokenization is deterministic.
It reuses the YAML seed corpus and dictionary. Run a short check with
`scripts/fuzz.roc smoke yaml-source`, or explore more locally with
`scripts/fuzz.roc campaign yaml-source --seconds 600`.

Structured targets (`csv-roundtrip`, `csv-decode`, `xml-roundtrip`,
`xml-malformed`, `xmlns-roundtrip`, `yaml-roundtrip`, `yaml-block`, `json-roundtrip`,
`http-roundtrip`, `http-smuggling`, `markdown-inline-ast`, `markdown-blocks`,
`markdown-refdefs`, `parser-combinators`):: The bytes are _choices_. A generator reads them to
build a value (a table, an XML tree, an HTTP message, a Markdown syntax tree)
and a way to write it down, and builds the expected parse alongside the text
from the specification, never by calling the parser. The target then requires
the parser to return exactly that value. Mutating generators such as
`xml-malformed` and `http-smuggling` instead inject one known violation into a
valid document and require the parser to reject it. `parser-combinators`
builds a random combinator expression and compares the real parser with a
small reference interpreter of the documented semantics.

Seeded targets (`csv`, `xml`, `yaml`, `http-request`, `http-response`):: The
original targets read a string through roc-fuzz's `Fuzz.str` generator. They
start from reviewable seeds in `fuzz/seeds/<name>.json`, which the runner
encodes for `Fuzz.str` at run time, and use the token lists in
`fuzz/dictionaries/` to mutate towards real syntax. Seed strings are limited to
255 UTF-8 bytes by that encoding.

Raw targets also take seeds and a dictionary, written as plain text. Structured
targets start from an empty corpus, because their bytes are not text.

The three JSON targets divide the work this way:

* `json-raw` reads the bytes with the default, strict options. Besides the
  checks every raw target makes, `JsonValue.parser` must agree with
  `parse_str`, an accepted value must write out (compact, indented and sorted)
  as text that reads back the same, and wrapping the input as `[x]` or
  `{"k":x}` must give the wrapped value. Inputs starting with `0xFF` build
  limit boundaries, large objects with a repeated key, and unclosed nesting.
  It starts from `fuzz/seeds/json.json` with `fuzz/dictionaries/json.dict`.
* `json-options` uses its first two bytes to choose a `JsonValue.Options`
  set, and checks that the options behave monotonically: adding a relaxation
  never rejects or changes a value that was accepted without it, and adding a
  check never accepts anything new. Its seeds in
  `fuzz/seeds/json-options.json` start with those two bytes.
* `json-roundtrip` generates a value, a set of options and a way to write the
  value, with relaxed syntax only where the options allow it, and requires
  the exact value, the exact compact and indented writer output, and the
  exact column of a repeated key.

== Oracles

A property test can only be as good as its expected answer. Structured targets
build that answer from the specification, but a generator can share a
misunderstanding with the parser. So each format is also compared with a
mature, independent implementation, its _oracle_, pinned to an exact version:

[cols="1,2,2",options="header"]
|===
|Format |Oracle |Specification and suite
|CSV |Python's `csv` module in strict mode |RFC 4180, plus the documented dialect
|XML |expat (Python's `pyexpat`) |XML 1.0 5th edition, W3C XML Conformance Test Suite 2013-09-23
|YAML |ruamel.yaml |YAML 1.2, the yaml-test-suite
|JSON |Python's `json` module, with the parse options modelled in `review_json.py` |RFC 8259, JSONTestSuite, and pinned SPDX, CycloneDX, Syft and Trivy documents
|HTTP |h11 |RFC 9112 and RFC 9110; cases pin where RFC 9112 is stricter than h11
|Markdown |cmark-gfm 0.29.0.gfm.13 (via `cmarkgfm`), with markdown-it-py to adjudicate |CommonMark 0.31.2 spec examples and GFM extensions
|===

Oracles have bugs too. When roc-parser and the oracle disagree, the review
reports it, and a person decides which one the specification supports. Known
oracle quirks are named in the review scripts and in the baselines, with the
section of the specification that settles them.

== Run the property tests

AsciiDoc adds `asciidoc-raw` for byte-input robustness and error locations,
and `asciidoc-structured` for independently constructed block trees.
Its broader oracle fixtures, generated corpus and mutation exploration are
described in <<asciidoc>>. Inline source agreement alone does not establish
agreement on Asciidoctor substitutions or rendered HTML.

Run every target for a short, iteration-bounded smoke test. This is what the
`fuzz` section of `blueprint run check` runs on a pull request; it builds shared executables with two compiler jobs, then runs each property in turn:

[source,bash]
----
scripts/fuzz.roc smoke all
----

Run one or more targets by name, and lower the iteration count for a quick
check while you work:

[source,bash]
----
scripts/fuzz.roc smoke csv --runs 200
----

The last lines of the output are the target's summary and its report:

[source,text]
----
csv: passed; baseline not_checked; examples 0; exploration passed (attempted 200, accepted 200, rejected 0)
Report: .roc-fuzz/reports/934809-521896414/report.json
----

Run a longer, time-bounded campaign on the target closest to your change. The
scheduled `fuzz.yml` workflow runs a 600-second campaign for every target each
night, on the latest Roc nightly:

[source,bash]
----
scripts/fuzz.roc campaign markdown-inline-ast --seconds 600
----

`--max-input-size`, `--timeout` and `--memory-limit` override a target's
registered bounds, and `--no-build` reuses the family's verified binary from
the last run. A family name such as `Records` selects all its properties.
`--platform PATH` replaces the released roc-fuzz platform with a local entry
point for upstream development; its sources and native host enter the build
identity.

The runner keeps everything under `.roc-parser-tmp/fuzz/`:

* `bin/<family>`: one shared executable and its build receipt;
* `corpus/<target>/`: the working corpus, which grows across runs;
* `runs/<target>/`: runner metadata, and the inputs of any failure.

== Reproduce and minimise a failure

A failing run prints the crash message and the paths of its report and of the
saved input, `original-input.bin`. In CI,
the `fuzz-failure-<target>` artifact holds the binary, the corpus and the run
directory. Use the same target name for every step.

. Show the input as the target decodes it. For a structured target this is the
generated document and its expected value:
+
[source,bash]
----
scripts/fuzz.roc show csv-roundtrip INPUT --no-build
----
. Replay it to confirm that it still fails:
+
[source,bash]
----
scripts/fuzz.roc replay csv-roundtrip INPUT --no-build
----
. Minimise it into a smaller input that fails the same way:
+
[source,bash]
----
scripts/fuzz.roc minimize csv-roundtrip INPUT OUTPUT --no-build
----

`INPUT` can be any file, including one from the corpus. Showing a corpus entry
of the seeded `csv` target prints the string it decodes to:

[source,bash]
----
scripts/fuzz.roc show csv .roc-parser-tmp/fuzz/corpus/csv/13d7ab0a19cc0856931196f0e8bac548e045234b --no-build
----

Output (the last line):

[source,text]
----
"a"
----

Each command writes a report under a `.roc-fuzz/` directory, which Git ignores.

== Add a regression

Once you understand the minimised input:

. Write the smallest `expect` in the module that fails for the same reason, and
  fix the parser until it passes. The `expect` is the regression; it runs in
  every build.
. For a seeded or raw target, add the readable input to
  `fuzz/seeds/<name>.json` so the fuzzer starts near the bug in future runs.
. If the generator of a structured target avoided the input's shape, remove
  that restriction so the target covers it from now on.
. Keep the raw minimised input and the target binary outside the repository
  when exact reproduction of a historical failure matters.

[#property-testing-fix-the-cause]
== Fix the cause, do not gate it

When a property fails, change the parser, not the test. Do not add a condition
to a target that skips the failing shape, a known-gaps flag, or a baseline
entry, to make CI green. A gate hides the bug from every later run, and the
fuzzer will not tell you when it comes back.

There are two legitimate exceptions, and both need a written reason:

* the input is outside the subset the module documents as supported (for
  example a DOCTYPE in XML, or multi-line flow collections in YAML); and
* the oracle is wrong and the specification says so.

Several gates that once existed were removed by fixing the parser, which is
how the targets found the CSV final-record bug, the YAML block scalar
chomping bugs and the quadratic Markdown inline cases.

== Run a conformance review

Each format has a review script that runs a small probe app,
`scripts/<format>/probe.roc`, which prints the parser's result as JSON, and
compares it with the oracle. Install the pinned oracle into a virtual
environment first:

[source,bash]
----
python3 -m venv .venv
.venv/bin/python -m pip install --no-deps -r scripts/yaml/requirements.txt
----

`scripts/http/`, `scripts/markdown/` and `scripts/yaml/` each have a
`requirements.txt` with every dependency pinned, so `--no-deps` installs
exactly the reviewed versions; CSV, XML and JSON use the Python standard
library. Cross-language comparisons run locally. `blueprint run conformance`
does all of this in one environment: with no arguments it runs the fast checks,
and `all` adds the robustness campaigns:

[source,bash]
----
.venv/bin/python scripts/review_yaml.py check --baseline scripts/yaml/known-failures.json
.venv/bin/python scripts/review_yaml.py campaign --smoke
python3 scripts/review_xml.py check --baseline scripts/xml/known-failures.json
python3 scripts/review_json.py check --baseline scripts/json/known-failures.json
python3 scripts/review_json.py campaign --smoke
python3 scripts/review_csv.py
.venv/bin/python scripts/review_http.py
----

The `campaign` commands are robustness campaigns. `review_json.py campaign`
gives 60% of its time budget to libFuzzer runs of the three JSON targets,
whose raw targets also start from every short case and suite input. It gives
the rest to a seeded differential loop that generates documents and option
sets, mutates them, and compares the probe with the oracle. It writes a report, and a reproducer
for each kind of disagreement, under `.roc-parser-tmp/json-review/campaign/`.
`--smoke` runs a short, iteration-bounded local comparison; for a longer run, pass a budget and a seed, and replay a reproducer once you have a
fix:

[source,bash]
----
python3 scripts/review_json.py campaign --seconds 1800 --seed 94
python3 scripts/review_json.py replay .roc-parser-tmp/json-review/campaign/reproducers/FILE.json
----

The CSV review runs the hand-written cases, 2000 seeded random inputs and,
with `--corpus DIR`, a fuzz corpus. Its last line summarises the run:

[source,text]
----
cases=2035 unexpected=0 known=0 fixed_known=0
----

The Markdown reviews compare against the CommonMark spec examples and
cmark-gfm:

[source,bash]
----
.venv/bin/python -m pip install --no-deps -r scripts/markdown/requirements.txt
.venv/bin/python scripts/review_markdown.py check
.venv/bin/python scripts/review_markdown_blocks.py check --baseline scripts/markdown/blocks/known-failures.json
----

Several scripts can also check a structured target's generator against the
oracle, which is how a generator's own mistakes are caught: `review_xml.py
corpus <target> <corpus>`, `review_json.py corpus <target> <corpus>`,
`review_http.py --corpus DIR --fuzz-show BINARY --fuzz-target http-roundtrip`,
`review_markdown.py generated BINARY CORPUS` and
`review_markdown_blocks.py crosscheck BINARY CORPUS --fuzz-target markdown-blocks`.

== Known-failures baselines

Each format keeps a baseline at `scripts/<format>/known-failures.json` (for
Markdown blocks, `scripts/markdown/blocks/known-failures.json`): the
cases where roc-parser and the oracle are allowed to disagree. Every entry
carries a reason, of one of these kinds:

* the input is valid but outside the documented subset;
* the oracle is wrong, citing the specification (for example, expat does not
  check `VersionNum`); or
* a documented design decision (for example, YAML mapping keys are their
  source text).

A review fails when a case disagrees and is not in the baseline, and reports
any baseline entry that now passes as stale. When your change makes a known
failure pass, remove the entry. When it introduces a new disagreement, fix the
parser; add an entry only for one of the reasons above. `review_yaml.py`,
`review_json.py` and `review_markdown_blocks.py` can rewrite the baseline with
`--record-known-failures PATH`; review the diff entry by entry before you
commit it.

== OpenSSF Scorecard

The OpenSSF Scorecard _Fuzzing_ check detects OSS-Fuzz, ClusterFuzzLite and a
few language-specific frameworks, but not Roc targets. A low Fuzzing score is a
detection gap, not evidence that these campaigns did not run.

== Local web-markup campaigns

The `html-raw`, `svg-raw`, `svg-path`, `mathml-raw`, `markup-source`, `markup-structured`,
`markup-limits` and `markup-segments` targets exercise malformed input,
independently generated structure, source partitioning, bounds and typed holes.
They are registered with `scheduled: False`. Run them locally using the commands
in xref:markup.adoc#markup[Parse HTML, SVG and MathML]. Their seeds and dictionaries
are reviewable source; corpus/report output remains in ignored scratch storage.

== Incremental document parsing

`stream-contract` compares shared adapters against an independent byte-record
model under arbitrary splits and injected source errors. `stream-ceilings`
measures distinct generated chunks inside the allocator measurement and discards
completed output. CSV, QIF and OFX add format-specific chunk equivalence,
round-trip, malformed-record and resource targets. They run in PR smoke and
scheduled campaigns through the same registry as the existing formats.

The financial reviews use pinned independent Python libraries and cross-writer
checks. Record-error recovery is checked against independently filtered expected
models; broken framing remains terminal. Source chunks, syntax boundaries and
encoding boundaries are independent fuzz choices.

== Check diagnostic ownership

Run `scripts/fuzz.roc smoke diagnostic-lifetimes` locally to check
that native JSON, YAML and CSV diagnostic payloads survive after their input
is dropped without retaining unrelated source bytes. Two-byte seeds choose a
failure kind and generated padding size; the property checks complete payload
identity and retained allocation size. XML error lifetimes are also checked by
`xml-stream-ceilings` alongside its reader and namespace bounds.
