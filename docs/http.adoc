[#http]
= HTTP messages
:idprefix: _
:idseparator: _

This chapter shows how to parse raw HTTP/1.x bytes into Roc records: a request
or response line, its header fields, and its body. It is a set of how-to guides
for readers who know basic Roc and are handling bytes from a socket, a test
fixture or a capture file. By the end you can read requests and responses,
decode chunked bodies, read messages incrementally, split pipelined messages,
embed the parsers in a larger grammar, and know which inputs the parser refuses
and why.

The `HTTP` module follows the message syntax of RFC 9112 and the field syntax
of RFC 9110. It parses messages; it does not open connections or send
anything.

[WARNING]
====
The complete-input APIs hold the whole message in memory and have no size
limits. Bound input before calling them on network data. For bounded metadata
and body fragments, use the incremental APIs in <<http-streaming>>.
====

[source,text]

A request is a record with these fields:

* `method`: a `Method`, one of `Get`, `Head`, `Post`, `Put`, `Delete`,
  `Connect`, `Options`, `Trace` or `Patch`, or `Extension(name)` for any other
  method token, such as `PURGE`. Method names are case-sensitive, so `get` is
  `Extension("get")`.
* `target`: the request target exactly as sent, such as `/notes?id=1`.
* `version`: a `Version`, `{ major, minor }`.
* `headers`: a `List(Header)` in the order received, where each `Header` is
  `{ name, value }`.
* `body`: the body bytes as a `List(U8)`.

[#http-framing]
== Understand how the body is found

The headers decide where the body ends (RFC 9112 section 6.3). The parser
applies these rules in order:

. A response with a `1xx`, `204` or `304` status has no body.
. `Transfer-Encoding: chunked` means the body is a series of chunks, which the
  parser decodes into one `body`.
. `Content-Length: n` means the body is exactly `n` bytes. If the input has
  fewer, parsing fails.
. With neither field, a request has no body, and a response's body runs to the
  end of the input, because the server marks the end by closing the
  connection.

[WARNING]
====
A response to a `HEAD` request, and a `2xx` response to a `CONNECT` request,
also has no body, but the parser cannot see the request that the response
answers. If you parse such a response as-is, rule 3 or 4 reads the following
bytes as its body. Handle those responses yourself: for example, stop after the
blank line that ends the header fields.
====

[#http-pipelined]
== Read pipelined messages

A client may send several requests on one connection without waiting for
responses. `HTTP.parse_request` consumes exactly one message and returns the
bytes that follow it as `rest`; parse `rest` again for the next message. To
read a whole buffer of requests at once, use `HTTP.parse_requests`, which
fails unless the buffer ends exactly at the end of a request:

[source,roc]
----

----

Output:

[source,text]
----

----

A response with no framing fields reads to the end of the input, so it is
always the last message in a buffer.

[#http-streaming]
== Read messages from byte chunks

Use `Streaming.read_stream(chunks, HTTP.request_decoder(props))` to process a request pipeline from a
file or socket without collecting its bodies. `chunks` is a
`Stream(Try(List(U8), source_error))`; the pure equivalent is
`Streaming.read_iter(chunks, HTTP.request_decoder(props))`. Empty chunks do not mean EOF, and
chunk boundaries may occur inside any HTTP line, UTF-8 header value, or body.

The reader emits `Value(RequestHead(head))`, followed by zero or more
`Value(Body(bytes))` fragments, any `Value(Trailer(header))` fields, and
`Value(MessageEnd)`. It then starts the next pipelined request. Bodies are
binary bytes, with chunked transfer framing removed. No complete body is
retained. A zero-length body produces no `Body` event.

`MessageEnd` validates one message. The final `Finished(report)` validates the
source through EOF; drain the reader through it to detect an incomplete next
message or malformed suffix. Stopping after a head or body fragment leaves the
remaining input unvalidated. A source failure is returned as
`Err(SourceErr(original_error))` and never completes a truncated message.
HTTP framing and limit failures are terminal `Err(ParseErr(error))` values,
with byte offsets counted from the start of the source. HTTP readers never
skip rejected messages or attempt to resume at another line.

The complete program {src}/examples/http-streaming.roc[`examples/http-streaming.roc`]
reads stdin and prints each message's body byte count. For example:

[source,sh]
----
printf 'POST /notes HTTP/1.1\r\nHost: a\r\nContent-Length: 2\r\n\r\nhi' | roc examples/http-streaming.roc
----

Output:

[source,text]
----
request /notes
body bytes: 2
finished; protocol bytes: 0
----

=== Associate responses with requests

Use `Streaming.read_stream(chunks, HTTP.response_decoder(methods, props))`
or `Streaming.read_iter` for responses. The decoder requires an `Iter(HTTP.Method)` containing the request methods in response
order. A response without a matching method is an error. An informational
response such as `100` or `103` produces its own head and `MessageEnd`, while
retaining the method for the final response. Methods are pulled only when a
response starts; unused methods are neither pulled nor checked at source EOF.

Responses to `HEAD`, informational responses, `204`, and `304` have no body.
A response without length or transfer framing streams its body until source
EOF, then emits `MessageEnd` and `Finished`. These readers retain the strict
framing checks of the complete-input API, including rejecting conflicting
framing fields even when response context implies an empty body.

A `101` response or successful `CONNECT` response ends HTTP parsing. After its
head and `MessageEnd`, the reader emits `ProtocolSwitch`, then bounded
`ProtocolData(bytes)` events containing the remaining bytes unchanged, through
source EOF. The application is responsible for validating the protocol upgrade
and interpreting those bytes. They are never parsed as another HTTP message.

The example accepts `get`, `head`, or `connect` to read responses for one
request of that method. For a response to `HEAD`:

[source,sh]
----
printf 'HTTP/1.1 200 OK\r\nContent-Length: 999\r\n\r\n' | roc examples/http-streaming.roc head
----

The reported body byte count is zero; the advertised length is metadata.

=== Bound metadata and output fragments

`HTTP.ReadProps` defaults to 65,536 head bytes, 8,192 bytes per line, 100 header
fields, 65,536 trailer-section bytes, 100 trailer fields, and 65,536 bytes per
body or protocol-data fragment. The byte limits include CRLF for complete
heads and trailer sections; `max_line_bytes` excludes CRLF and also bounds
chunk-size lines and their extensions. Each message starts new head and trailer
budgets. `max_body_chunk_bytes` must be positive.

The props are `max_head_bytes`, `max_line_bytes`, `max_headers`,
`max_trailer_bytes`, `max_trailers`, and `max_body_chunk_bytes`. Limits fail
before retaining the byte or emitting the field that exceeds the budget.
`Host`, `Content-Length`, and `Transfer-Encoding` are rejected in trailers.
Retained parser memory depends on these metadata bounds and the current source
chunk. Keeping emitted values intentionally adds to application memory use.
These limits do not bound the total body length, connection lifetime, or time
spent waiting for input; enforce those in the application when needed.

For a custom driver, `HTTP.request_decoder(props)` or
`HTTP.response_decoder(methods, props)` returns a shared `Streaming.Decoder`.
`decoder.step(bytes, More)` returns at most one event and the number of
bytes consumed from that call. Supply `Final` only when the source has ended,
and continue stepping to the terminal result. The shared
xref:streaming.adoc#streaming[chunk reader contract] describes consumption and
completion in detail.

[#http-security]
== Rejected messages and request smuggling

_Request smuggling_ happens when two programs, such as a proxy and your
server, disagree about where one message ends and the next begins. An attacker
can then hide a second request inside the first one's body. To avoid this, the
parser rejects any message whose framing it would otherwise have to guess.

[IMPORTANT]
====
A rejected message is not safe to recover from. Do not retry it with a
"cleaned-up" copy, and do not keep reading the same connection: close it. If a
proxy in front of your server accepts a message this parser rejects, the two
disagree about framing.
====

The parser rejects a message that has any of the following:

* Both `Transfer-Encoding` and `Content-Length`.
* More than one `Content-Length` value, unless every value is identical, or a
  value that is not plain decimal digits (for example `+4`), or a value with
  more than 19 significant digits.
* Any transfer coding other than exactly one `chunked`, such as
  `chunked, gzip`, `gzip`, or `chunked` given twice.
* `Transfer-Encoding` in an HTTP/1.0 message.
* Whitespace between a field name and its colon, as in `Transfer-Encoding :`.
* Obsolete line folding (a field line that starts with a space or tab).
* A line ending other than CRLF: a bare CR or a bare LF anywhere in the head
  or in chunk framing.
* Control characters in a field value or reason phrase, or a field value that
  is not valid UTF-8.
* In an HTTP/1.1 request, a missing `Host` field; in any request, more than
  one `Host` field.
* A malformed chunk size, such as `5 ` with a trailing space, or one with more than 15 significant hexadecimal digits.

The status line has rules of its own: the status code is exactly three digits
and at least `100`, and the space before the reason phrase may be left out
when the phrase is empty.

`parse_request` and `parse_response` fail with `InvalidHttp(Error)`, where an
`Error` is `{ offset, problem }`: the tag identifies the broken rule and
the offset is the byte where the problem is. A framing error points at the
start of the field line responsible; a missing `Host` field is reported at
offset 0, the start of the message.

== Out of scope

* Request context in the complete-input response APIs; use
  <<http-streaming>> for `HEAD` and `CONNECT` responses.
* Preserving chunk extensions. Trailer fields are emitted by incremental
  readers and validated then dropped by the complete-input APIs.
* Content codings such as gzip, and any `Transfer-Encoding` other than
  `chunked`, which is rejected rather than decoded.
* HTTP/2 and HTTP/3, which are binary protocols.
* Total body-size limits and timeouts, which the caller must enforce.
  Incremental readers provide metadata and fragment limits.

The {api}[API reference] lists the `HTTP` types and parsers.

[#http-performance]
== Performance

A typical request or response head parses in 1.5–2 µs on an Apple M2, as
fast as Go's `net/http` and about 3 times slower than Rust's httparse, which
checks less (see <<performance-fairness>>). Line ends, tokens and field
values are checked 16 bytes at a time with SIMD. A
`Content-Length` body is returned without copying, so body size barely
affects the time; a chunked body is assembled once, in linear time even with
thousands of one-byte chunks (20,000 of them in 0.7 ms). See <<performance>>
for the measurements.
