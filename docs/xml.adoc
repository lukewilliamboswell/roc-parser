[#xml]
= Read XML documents
:idprefix: _
:idseparator: _

This chapter shows how to parse an XML document into a tree, find elements,
attributes and text in it, and report malformed input with a line and column.
It also shows how to read untrusted or very large documents, resolve
namespaces, and write a document back out. It is for Roc programmers who have
added `parser` to their app's dependencies and need data out of XML such as
feeds, SVG files, office documents or configuration.

The parser checks that a document is well-formed according to XML 1.0 and
gives you the tree after the usual XML clean-up: references replaced by their
text, line endings normalised, comments dropped. It does not validate against
a schema or DTD, and it rejects documents that contain a `<!DOCTYPE>`; see
<<xml-unsupported,what is not supported>> before using it on documents from
other tools.

Every example on this page comes from
link:{src}/docs/examples/xml-guide.roc[`docs/examples/xml-guide.roc`], which
CI runs, and imports `parser.Xml` and `parser.XmlNs`.

== Parse a document and find elements

`Xml.parse_str` takes the whole document and returns an `Xml` record with
the document's `root` element and its `declaration`. Each node in the tree
is one of:

[source,roc]
----
Node := [
    Element({ name : Str, attributes : List(Attribute), children : List(Node) }),
    Text(Str),
]
----

An `Element` holds its name, its attributes in source order, and its
children. There is no query language, but `Xml.Node` has four helpers for
the common lookups, and you can pattern match on the tree for anything else:

* `node.name()` is `Ok(name)` for an element and `Err(NotAnElement)` for text.
* `node.attribute(name)` is the attribute's value, or `Err(Missing)`.
* `node.children_named(name)` lists the direct child elements with that name.
* `node.text()` joins all text inside the node, like the DOM's `textContent`.

The whitespace between elements is kept as `Text` nodes; `children_named`

character reference `&#x1F600;` have already been turned into ordinary text.

== What the tree contains

The tree is what an XML processor reports, not the literal source:

* The five predefined entities `&lt;` `&gt;` `&amp;` `&apos;` `&quot;` and
  decimal (`&#65;`) or hexadecimal (`&#x42;`) character references are
  replaced by their characters, in text and in attribute values.
* CDATA sections become text, and adjacent text, including text on both
  sides of a comment, is merged into one `Text` node.
* Line endings (`\r\n` and lone `\r`) become `\n`.
* In attribute values, tabs and line breaks become spaces.
* Comments and processing instructions are checked and then dropped.
* The XML declaration is available as `declaration`: `Ok({ version,
  encoding })` or `Err(Missing)`. The version is a record such as
  `{ major: 1, minor: 0 }`, and the encoding is `Err(Missing)` when the
  declaration does not name one.

== Report malformed input

When a document is not well-formed, `Xml.parse_str` returns
`InvalidXml({ line, column, message })`. Lines and columns are one-based, and
columns count UTF-8 bytes, so a column after non-ASCII text is larger than the
number of characters a user sees.

for the next parser. Its failures are `ParseError({ message, offset })`, with
the same message as `Xml.parse_str` and the byte offset of the problem.

[#xml-untrusted]
== Read untrusted documents

`Xml.parse_str` sets no limits, so a hostile document can make it build a
very large tree. `Xml.parse` takes `Xml.ReaderProps`, whose fields all have
defaults: `max_depth` (1,024), `max_elements` (4,194,304) and
`max_attributes` per element (1,024). A document that would exceed one fails

[#xml-reader]
== Read a large document an element at a time

`Xml.reader` returns an `Xml.Reader` positioned before the root element.
Each call to `next` returns the next `Event`, `Start({ name, attributes })`,
`End(name)` or `Text(text)`, with the reader after it, then `Done` at the end
of the document, or `Failed(error)`. The events match the tree: `<a/>` is a
`Start` and an `End`, text is merged as in the tree, and comments are
dropped. Directly after a `Start`, `element` builds that element's subtree
and continues after its end tag, so a program can keep one small tree at a
time instead of the whole document:

that keeps no events holds memory for the open elements only. The same
limits apply as for `Xml.parse`, and `location` gives the line and column of
the most recent event.

[#xml-namespaces]
== Resolve namespaces

`XmlNs` processes namespaces following Namespaces in XML 1.0. Each element and
attribute name becomes `{ namespace, local, prefix }`, where `namespace` is
`Uri(uri)` or `NoNamespace`. A binding covers its element and descendants,
`xmlns=""` removes the default namespace, unprefixed attributes are in no
namespace, and `xml` is always bound. The `xmlns` declarations become each
element's `bindings`. Look elements up by namespace and local name, so the
same code reads both spellings of an Atom feed:

A namespace problem, such as an undeclared prefix, a reserved prefix bound
to the wrong namespace or two attributes with the same expanded name, is
`InvalidNamespace({ problem, line, column })` at the start tag. `XmlNs`
mirrors `Xml`: `XmlNs.parse` takes the same limits, and `XmlNs.reader`
resolves names while it reads, so only one tree is built.

[#xml-write]
== Write a document

`XmlNs.render` writes a namespaced tree as XML 1.0 text. By default it
writes the tree's own prefixes and declarations, so a parsed document is
written as it was read. `prefixes: Table(entries)` writes every name with
its namespace's prefix from the table instead, declared once; an empty prefix
makes a namespace the default. Text and attribute values are escaped so that
they read back unchanged. A tree that cannot be written, with a name that is
not allowed, a character XML 1.0 does not allow, or a prefix not bound where
it is used, fails with `Unrenderable({ problem, path })`.

[#xml-unsupported]
== What is not supported

These limits are by design:

Document type declarations:: A `<!DOCTYPE ...>` is rejected. As a result only
the five predefined entities exist, and any other reference, such as
`&nbsp;`, is an error. Replace HTML entities with character references
(`&#160;`) before parsing.
Namespaces in Xml:: `Xml` keeps names exactly as written: `svg:path` is an
element named `"svg:path"`, and `xmlns` declarations are ordinary
attributes. Use `XmlNs` to resolve them.
Declared encodings:: The input is a Roc `Str`, which is already UTF-8. An
`encoding="..."` in the declaration is reported in `declaration` but not
used. Convert other encodings to UTF-8 before parsing.
Validation:: Only well-formedness is checked. Required elements, attribute
types and schemas are not.

For the full module interfaces, see the link:{api}Xml[Xml] and
link:{api}XmlNs[XmlNs] API references.

[#xml-performance]
== Performance

`Xml.parse_str` builds the tree at about 120–135 MB/s on an Apple M2, and the
rate stays flat from 4 KiB to 1 MiB documents: the parser is linear in the
input size. On the generated documents that is about 2.2 times as fast as
Go's `encoding/xml`, and 1.4–2 times slower than Rust's quick-xml and
roxmltree. Character data and attribute values are found 16 bytes at a time
with SIMD, the input is validated as UTF-8 once, and names, text and
attribute values with nothing to unescape are slices of the input string,
so they keep the input alive.
Elements are parsed with an explicit stack, so 5,000 levels of nesting are
safe, and duplicate-attribute checks are linear: an element with 5,000
attributes parses 19 times faster than with the Rust libraries. Decoding text
and attribute values is linear however they mix references, line endings and
CDATA, and the `xml-ceilings` fuzz target holds every reading path to
allocation ceilings linear in the document.

Reading every event with `Xml.reader` takes about 70% of the time
`Xml.parse_str` takes to build the whole tree. `XmlNs.parse_str` runs at about
a third of `Xml.parse_str`'s speed on an OOXML-like document, since it splits
and resolves every name and its nodes are larger; it holds about twice the
memory. See <<performance>> for the measurements and caveats.
