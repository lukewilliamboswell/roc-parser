[#adding-a-format]
= Add a format module

This how-to is for contributors who want to add a ready-made parser for a new
text format, alongside `CSV`, `Xml`, `Yaml`, `JsonValue`, `Markdown` and
`HTTP`. It assumes <<contributing>> and <<property-testing>>, and that you have
opened an issue to agree that the format belongs in the package. When you
finish, the new module has the same evidence behind it as the existing ones:
tests, a review against a mature implementation, property tests in CI,
benchmarks, and a chapter in this manual.

The steps use a hypothetical format called `Toml` as the example. Follow them
in order: each step relies on the one before.

== 1. Decide what you support

Write down, before any code, which specification and version the module
follows, and which parts of it the module supports. Every existing module
supports a documented subset and rejects the rest with an error, rather than
misreading it. For example `Xml` rejects a DOCTYPE, and `Yaml` rejects
multi-line flow collections. A rejected input is a clear limit; a misread one
is a bug that nobody notices.

Pick the oracle now too: a widely used implementation that you can pin to an
exact version and call from Python, such as `tomllib` for TOML. The oracles of
the existing formats are listed in <<property-testing>>.

== 2. Create the module

. Add `package/Toml.roc`. Start it with a `##` doc comment that names the
  specification, lists what is supported and what is rejected, and describes
  the error type. This comment becomes the module's page in the API reference.
. Give every exposed value a `##` doc comment with its purpose and, where it
  helps, a short `expect` example.
. Expose the module in `package/main.roc` and name it in that file's doc
  comment. `roc test package/main.roc`, which `scripts/all_tests.py` runs,
  then runs its tests with the rest.
. Check that the name does not clash with a builtin module that Roc imports
  automatically. Roc has a builtin `Json`, so `import parser.Json` would
  leave the alias unbound; that is why the JSON module is `JsonValue`.
. Make it a type module and follow the conventions of the existing ones:
** `Toml.parse_str : Str -> Try(Toml, [InvalidToml(Toml.Error)])`, where
   `Toml.Error` is a record with a `message` and the most precise location
   the format has (`line` and `column` for a text format);
** `Toml.parser : Parser(Utf8.Bytes, Toml)` for callers who compose
   parsers, failing with `ParseError({ message, offset })`;
** `Try(a, [Missing])` for every optional value, and methods in the
   `.{ }` block, called in method-call style in examples;
** fallible parsing and validation functions return errors on every input;
   explicit constant assertions such as `Literal.require` are documented separately.
. If records are a natural target, also implement a format for
  type-directed decoding, as `CSV.Format` and `Yaml.Format` do, and expose
  `Toml.decode` with a `Parseable` where-clause alias. The parsers chapter of
  the Roc language reference lists the methods a format provides.

Prefer a scanner over the input bytes for document-level parsing, with an
explicit stack for nesting. The combinator style is convenient for small
grammars, but every rewritten module (CSV, XML, HTTP, Markdown) moved to
scanners to stay linear in the input size and to avoid deep recursion, and
`JsonValue` was written as one from the start.

If the format has common variants, or callers need checks beyond the
specification, give the module a `parse_with` that takes a nominal options
record with defaulted fields, as `JsonValue.Options` does. Make the defaults
the strict specification, and make each relaxation and each extra check a
field that is off by default, so `parse_str(text)` is `parse_with(text, {})`
and nobody gets a relaxation they did not ask for. Keep each option's code at
one check site, test every field at and past its boundary, and pass the same
record through the validation props, so that compile-time and run-time
checks agree.

Compile-time parsing is an enduring requirement for format modules. Make the
document type nominal and implement `from_quote` by delegating to a checked
`validate` function returning `Try(Toml, [BadQuotedBytes(Str)])`. Use a nominal
props record with defaulted fields for the source name, format options, and
configurable extra checks. Add `validate_as` when type-directed decoding is
supported. Keep ordinary parsing acceptance unchanged. See
<<compile-time-parsing>> for the quotation and imported-file contract.

== 3. Write the tests

Put `expect` tests next to the code they cover. For every rule, test an input
that is accepted, one that is rejected, and the boundary between them. Add a
test for each limit you chose in step 1.

Add compiler fixtures for valid and invalid quotations and imported text,
including default checks and overrides, to `scripts/literals/cases.json`, and
add `import parser.Toml` to the app header that `app_source` in
`scripts/check_literals.py` writes. The script checks rejection by both
`roc check` and `roc build`, and verifies the intended error message rather
than accepting any compiler failure.

Run the package tests:

[source,bash]
----
$ROC test package/Toml.roc
$ROC test package/main.roc
----

== 4. Add a probe and a review script

A conformance review runs the same inputs through your module and the oracle
and compares the results. It needs three pieces under `scripts/toml/`, modelled
on `scripts/csv/`, the smallest of the existing reviews:

`probe.roc`:: A basic-cli app that reads one document on standard input and
prints one JSON line: the parsed value or an error. Use the public API only.
`cases.json`:: Hand-written cases with a `name` and an `input`, one for each
rule and each known edge case. Add the specification's own examples or test
suite if there is one, pinned by URL and SHA-256 as `scripts/review_xml.py`
does for the W3C suite, or vendored as described below.
`known-failures.json`:: The baseline. It starts empty; every entry added later
needs a reason (see <<property-testing>>).

Then add `scripts/review_toml.py`. It builds the probe with `$ROC` (falling
back to `roc` on `PATH`), runs every case through the probe and the oracle,
converts both results to the same shape, and exits non-zero on any
disagreement that is not in the baseline. Report baseline entries that now
pass as stale. If the oracle is a third-party package, pin it, and all of its
dependencies, in `scripts/toml/requirements.txt` so that
`pip install --no-deps -r` installs exactly the reviewed versions.

To vendor a third-party test suite instead of downloading it, convert it to
one file, such as `scripts/toml/suite.json`, that records the upstream
repository and revision in a `source` object, and commit the suite's licence
beside it. `scripts/yaml/suite.json` with `YAML-TEST-SUITE-LICENSE`, and
`scripts/json/suite.json` with `JSONTESTSUITE-LICENSE`, are the models. Check
that the licence allows redistribution, and give the script a command that
regenerates the file from a checkout, like `review_json.py vendor-suite`.
Where the suite says an input is valid but your module rejects it by design,
label the case a policy deviation with its reason, as `review_json.py` does
for repeated keys, rather than hiding it.

Run it, fix the parser until it passes, and add a unit test under
`scripts/tests/` for any logic in the script that is not a direct call to the
oracle.

== 5. Add property-test targets

Add at least two targets under `fuzz/`, as described in <<property-testing>>:

`toml-raw.roc`:: Raw bytes. Check that the parser never crashes, that errors
point inside the input, and the metamorphic relations that hold for the format,
such as line-ending equivalence. Bound pathological shapes with the runner's
`--timeout`.
`toml-roundtrip.roc`:: A structured generator. Build a value and a way of
writing it from the bytes, build the expected result from the specification
without calling the parser, and require the parser to return exactly that
value.

Check the generator against the oracle on a corpus before you trust it: add a
`corpus` mode to the review script, like `review_xml.py corpus`.

Then add a robustness campaign to the review script: a `campaign` command,
like `review_yaml.py campaign` and `review_json.py campaign`. It spends part
of a time budget on libFuzzer runs of your targets and the rest on a seeded
differential loop that generates and mutates documents, runs each through the
probe and the oracle, and writes a report and a reproducer for every kind of
disagreement under `.roc-parser-tmp/`. Give it `--smoke` for a short,
iteration-bounded run in CI, `--seconds` and `--seed` for local runs, and a
`replay` command for a saved reproducer.

== 6. Register the targets

. Add each target to `TARGETS` in `scripts/run_fuzz.py`, with its seed
  encoding (`raw` for raw bytes, none for a structured target), seeds,
  dictionary, input size and timeout.
. Add reviewable seeds in `fuzz/seeds/toml.json` and syntax tokens in
  `fuzz/dictionaries/toml.dict` for the raw target.
. Add each target to the `target` matrix of the `fuzz` job in
  `.github/workflows/fuzz.yml`, in the same order as in `TARGETS`, which
  `TARGET_ORDER` in `scripts/run_fuzz.py` follows. Register the review in
  `REVIEWS` in `scripts/check_conformance.py`, with its command and
  `requirements` file, and the campaign's `--smoke` run as a second, scheduled
  entry, as `json` and `json-robustness` do; then add both to the `review`
  matrix of the `conformance` job in `fuzz.yml`, in the same order.

`scripts/tests/test_run_fuzz.py` fails if a `fuzz/*.roc` file is not
registered, or if the workflow matrix lists the targets differently, or in a
different order, from the registry; `scripts/tests/test_check.py` does the same
for the reviews. Every pull request runs the new targets and the fast review
through `blueprint run check`. Check the registries and run the new targets:

[source,bash]
----
python3 -m unittest discover -s scripts/tests -p "test_*.py"
python3 scripts/run_fuzz.py smoke toml-raw toml-roundtrip
----

== 7. Add a benchmark

Follow "Add a benchmark" in <<benchmarks>>: add `bench/roc/toml.roc`, which
calls the public entry point through `Bench.run!`, a branch in
`bench/roc/alloc.roc`, a deterministic generator and `pathological` entries in
`scripts/bench.py`, a frozen sample, and at least one comparator per language,
pinned exactly. `scripts/tests/test_bench.py` fails until the format has all
of them. Check that the pathological documents scale linearly; the allocation
counts from `--allocations` are a steadier signal than the timings:

[source,bash]
----
python3 scripts/bench.py --quick --formats toml
python3 -m unittest discover -s scripts/tests -p "test_bench.py"
----

== 8. Document the module

. Add a chapter `docs/toml.adoc` that shows how to parse a document, how to
  handle errors, and what is and is not supported. Include it from the manual's
  index with `leveloffset=+1`, like the other format chapters.
. Make every code example in the chapter a complete program that
  `scripts/check_doc_examples.py` compiles and runs, so it cannot drift from
  the API.
. Add the module wherever the manual lists the formats: the format table in
  `README.md`, the lists in `docs/index.adoc`, and `modules.adoc`,
  `overview.adoc`, `errors.adoc`, `compile-time-parsing.adoc`,
  `conformance.adoc`, `property-testing.adoc` and `performance.adoc`.
. Add the module to the release notes for the next version in
  `docs/releases/`.

Build and check the documentation:

[source,bash]
----
python3 scripts/build_docs.py --check
python3 scripts/check_doc_examples.py
python3 scripts/build_manual.py
----

== Checklist

* [ ] Supported subset and oracle written down in the module doc comment
* [ ] Module exposed in `package/main.roc` and named in its doc comment, with
  a name that no builtin module uses
* [ ] Strict defaults, with relaxations and extra checks in a defaulted
  options record
* [ ] `expect` tests for accepted, rejected and boundary inputs
* [ ] Compile-time fixtures in `scripts/literals/cases.json`, and the import
  in `app_source` in `scripts/check_literals.py`
* [ ] Probe, cases, review script and empty baseline under `scripts/`
* [ ] Any vendored test suite recorded with its revision and licence
* [ ] Raw and structured fuzz targets, registered in `run_fuzz.py` and in
  `fuzz.yml` in the same order
* [ ] A robustness `campaign` in the review script, with its `--smoke` run
  registered in `check_conformance.py` and the `conformance` matrix
* [ ] A benchmark driver, generator, samples and comparators
* [ ] Chapter with tested examples, the format added to every list of
  formats, and a release notes entry
