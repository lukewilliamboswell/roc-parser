[#benchmarks]
= Benchmarks
:idprefix: _
:idseparator: _

This chapter is for contributors who want to measure a change, add a
benchmark or reproduce the figures in <<performance>>. It covers the harness,
the corpora, the comparison programs, the environments the benchmarks run in,
and how to read a report.

== Run the benchmarks

You need a recent Roc nightly; the report records which one. Go,
Rust (cargo, Rust 1.98 or newer for the financial comparators) and Python 3
are needed only to create or qualify the corresponding reference measurements.
Use Python 3.10–3.13 for Quiffen; Blueprint's benchmark environment supplies 3.13.
Ordinary runs rebuild and measure Roc, then reuse qualified reference timings.
A missing or incompatible reference is reported as `ReferenceUnavailable`; it
is never silently rebuilt or remeasured.

[source,console]
----
$ export ROC=~/roc_nightly-macos_apple_silicon-2026-10-21-5349569/roc
$ python3 scripts/bench.py --quick --refresh-references  # explicitly create reference timings
$ python3 scripts/bench.py --quick --label candidate     # rerun only Roc; reuse references
$ python3 scripts/bench.py --allocations                  # full settings require their own reference cache
----

`--quick` measures each format's samples, its small generated document and one
pathological document, with three short batches. Use it to check that nothing
is broken, not to compare numbers. The full run takes about half an hour on a
laptop when refreshing all implementations. Cached reference timings are reused
without building or benchmarking Go, Rust or Python. Cheap runtime/version
probes qualify the cache; they do not parse the benchmark corpus.

Narrow a run with these options:

`--formats csv,xml`:: Only these formats.
`--langs roc,go`:: Only these implementations (`roc`, `rust`, `go`, `python`).
`--only large,sample-svg`:: Only documents with these names or kinds (`sample`,
`small`, `medium`, `large`, `pathological`).
`--label before`:: Write the report to `.roc-parser-tmp/bench/before/`, so two
runs can be compared side by side.
`--repetitions`, `--target-ms`, `--timeout`:: Batch count, approximate batch
duration and the time limit for one batch.
`--corpus-only`:: Write the corpus and its manifest, then stop.
`--refresh-references`:: Explicitly build and measure selected reference libraries,
then store their complete measurement receipts. This is the only mode that
creates a comparator Python environment or installs its dependencies.
`--reference-cache-dir`:: Share a cache across worktrees or output directories.
The default is `.roc-parser-tmp/bench/reference-cache`, separate from report labels.

To compare two revisions of the parser, check each one out in turn and run the
harness with a different `--label`; the report records the commit and whether
the tree was dirty. Use the same reference cache for both revisions; parser,
Roc compiler, and Roc benchmark-driver changes do not invalidate its entries.

Reference keys include the exact input SHA-256, comparator code and dependency
pins, installed runtime/library versions, build recipe, ownership/workload,
measurement settings, and machine/CPU-affinity/governor/resource configuration.
Changing any of these requires an explicit reference refresh. Go builds and
identity probes use `GOTOOLCHAIN=local`; select an installed Go compiler on
`PATH`, because cache qualification must not download toolchains. Rust identity
probes also disable automatic toolchain installation.

Cache files retain calibration, warmup and every measured batch, original
commands, timestamps and source-report provenance. Corrupt, stale or incomplete
receipts are rejected. Reports mark cache hits and preserve their original
measurement date: reused timings are historical measurements, not fresh timing
samples. They have no time-based expiry; refresh explicitly when new reference
measurements are needed. This measurement cache is separate from the shared
<<correctness-oracle-cache,correctness oracle cache>>: performance depends on runtime, hardware and
measurement conditions as well as the input.

Reference receipts persist in the local cache. A different machine configuration
reports `ReferenceUnavailable` and requires an explicit reference refresh rather
than reusing timings from another machine. Cross-language comparisons run locally.

[#streaming-performance]
== Measure streaming performance and elapsed-time targets

Measure record and event consumption separately from whole-document collection:

[source,console]
----
$ blueprint run streaming-bench -- --only medium --refresh-references --label streaming-before
$ blueprint run streaming-bench -- --only medium --label streaming-after --max-slowdown 1.5
----

The first command explicitly builds and measures the pinned Rust references;
the second rebuilds Roc and reuses matching reference receipts. The JSON
corpora contain the generated SBOM's component records as an array or NDJSON,
preserving number spellings. XML consumes decoded events without a tree. HTTP
includes header-heavy request pipelines; large opaque bodies are separate
workloads and cannot stand in for header parsing. The source is preloaded,
with I/O excluded from the timer. `--chunk-bytes` sets Roc's source chunk width
(4,096 by default); file-source memory is checked by the stream allocation
fuzz targets instead.

The references use `serde_json` owned values discarded one record at a time,
`quick-xml` borrowed events, and `httparse` borrowed heads with body/trailer
framing. XML's event checksum coalesces adjacent text and decodes references
and line endings. The report keeps ownership/workload labels; a matching
checksum does not establish identical validation or lifetime guarantees.
`Xml.reader` is also timed as a complete-source event reader for comparison.
Consumer checksums must agree. JSON's original-number and serde-normalized
number spellings use separate expected checksums computed from an independent
input model outside the timer; an unexplained mismatch cannot pass.

`--max-slowdown 1.5` requires each selected non-pathological Roc measurement
to take at most 1.5 times the fastest qualified reference's elapsed time.
It works for ordinary whole-document benchmark runs too. Collection and
consumption are compared separately. A missing reference, failed Roc parse,
or timing spread above 25% cannot pass; a noisy fastest reference must be
remeasured rather than replaced by a slower library. The command exits with
status one when a target fails or lacks qualified evidence. Detailed results
and target decisions are saved in `results.json` and `report.md`.

On macOS the harness cannot pin CPU affinity. Run final measurements serially
on an otherwise idle machine, retain the reported timing spread, and compare
revisions on the same hardware and toolchains. The README runner below uses
CPU affinity on Linux for its published figures.

Keep raw timing reports and reference receipts in the ignored
`.roc-parser-tmp/bench/` directory. Share reports as review or release attachments
when needed; commit the harness and concise result summaries rather than
machine-specific measurements.

== Reproduce the README throughput table

On Linux, choose an available logical CPU and run:

[source,console]
----
$ python3 scripts/readme_throughput.py --cpu 3
$ python3 scripts/readme_throughput.py --cpu 3 --refresh-references  # explicit initial reference measurement
----

The runner builds Roc drivers serially with `--opt=speed --debug`, then pins
the timed runs to that CPU. It parses one deterministic document for each
concrete README format, constructs the result and consumes a
checksum. CSV collects string rows with `CSV.parse_string_records`; QIF and
OFX use whole-document collection. The markup formats
use validated fragments with explicit namespace roots for SVG and MathML.
Documents are about 64 KiB, except HTTP, which uses a
555-byte browser GET request with realistic headers and no body. Opaque body
bytes would inflate throughput without adding parsing work. AsciiDoc parses
without rendering, and Roc source produces a complete lossless syntax tree.
These are representative workloads, not cross-format speed comparisons.

Each number is decimal MB/s from the median of seven calibrated batches
targeting 200 ms after warmup. The iteration cap can produce shorter batches.
Reading stdin and printing results are outside the
timer. Rejected inputs, unstable checksums and runs with more than 25% timing
spread cannot supply a published number. The runner leaves inputs, build logs
and full measurement receipts in `.roc-parser-tmp/readme-throughput/`.
The local `results.json` records its source hash, compiler, hardware, input hashes
and samples; changing Roc requires a new run.
The default rebuilds and measures Roc and reuses qualified reference timings.
`--refresh-references` explicitly builds and remeasures the reference parsers,
replacing their cached measurements. Refresh needs the Go/Rust/Python comparison toolchains, Ruby 3.4
or newer, and Zig 0.17.0 for the pinned compiler parser; `blueprint shell`
provides the pinned Zig. `--python` selects an existing interpreter with the
standard comparator pins; markup references use a separate virtual environment.
`--reference-cache-dir` selects the shared measurement cache.

The table selects the fastest successful collection reference from the measured
candidates. Borrowed results remain labeled, and known canonical/checksum
failures cannot win. Namespace-resolved DOM references for HTML, SVG and MathML
perform tree construction; Roc additionally retains source and performs
authoring validation. QIF's borrowed Rust reference uses floating-point amounts.
Other parsers also construct their own tree models, including the compiler's
tokenizer/AST versus RocSyntax's lossless indexed tree. These distinctions are
retained with library versions and original reference receipts; no aggregate
speed ratio assumes identical semantics or ownership. Current Roc DOM outputs
are checked against cached independent canonical evidence on every run.

== How a measurement works

Every implementation, in Roc or in another language, is a small program that
follows one protocol. It reads a document from standard input, starts a
monotonic clock, parses the
document a given number of times, stops the clock, and prints one JSON line:

[source,json]
----
{"iterations":120,"elapsed_ns":20414000,"successes":120,"checksum":43811}
----

Process start-up, reading the input and printing are outside the timed region.
Collection comparators build their in-memory result and fold over it into a
checksum. Comparators labelled `consume` discard each completed record and
reuse buffers where the library permits. Roc's CSV, QIF and OFX consumption
drivers pass preloaded input through the public streaming APIs in 64 KiB
chunks, validate each record, and consume the same decoded field checksums as
their collection drivers without collecting a document. Compare collection
and consumption workloads separately; the financial references currently
provide collection comparisons only.

These drivers preload the source: their RSS includes the complete input and
does not establish bounded file-source memory. Use
`bench/roc/csv-file-stream.roc` for a file/stdin source that retains bounded
read buffers and includes reading in its timing. Its checksum weights raw
field bytes directly, including bytes that are not valid UTF-8.

QIF compares typed bank transactions with Quiffen and Rust `qif_parser`.
Rust QIF retains borrowed strings and uses `f64` amounts rather than Roc’s
exact monetary values. It is reported as `collect-borrowed` and excluded from
ratios against owned collection. Rust `roxmltree` also borrows from the input
and is excluded from owned-collection ratios. Either can appear as the fastest
measured collection reference when the table labels these differences explicitly. The report lists each
implementation's representation and workload.
OFX compares bank/card statements with ofxtools, ofxparse, ofxgo, and Rust
`ofx-rs`. Financial checksums include transaction counts and weighted UTF-8
payee/name and memo bytes; exact amounts and dates are checked by the correctness
reviews. CSV checksums include every decoded field byte. The Go QIF slot has no
comparator because the surveyed Go reader does not provide the required coverage.

When several Rust toolchains are installed, select the intended one explicitly,
for example `RUSTUP_TOOLCHAIN=1.98.1 python3 scripts/bench.py --formats qif,ofx`.
The report records the selected compiler and locked library versions.

For each document and implementation, `scripts/bench.py`:

. runs one parse to estimate its cost, and picks the number of parses per batch
  so a batch takes about `--target-ms` (200 ms, or 20 ms with `--quick`);
. runs one warmup batch and discards it;
. runs `--repetitions` batches (7, or 3 with `--quick`), each in a fresh
  process;
. records the median time per parse, the minimum, maximum, standard deviation
  and spread (`(max - min) / median`), throughput in MB/s (1,000,000 bytes per
  second, from the median), and the peak resident set size of the batch
  processes;
. with `--allocations`, replays the document once through
  link:{src}/bench/roc/alloc.roc[`bench/roc/alloc.roc`], a diagnostic built
  with `roc build --fuzz`, and records how many times the Roc parser called
  `roc_alloc` for it, using the target's `measure` command.

Peak RSS is the whole process, so it includes the language runtime: about
1.5 MiB for Roc and Rust, 12–20 MiB for Go and Python, before any document is
read. Compare it within a language or across document sizes, not as an
absolute cost of a parser.

== Corpora

The corpus is generated by `build_corpus` in
link:{src}/scripts/bench.py[`scripts/bench.py`] every run. Each generated
document uses a random number generator seeded from its own name, so the
bytes, and the SHA-256 recorded for each one in the report, are identical on
every machine and run. Changing a generator changes the hashes, which marks
results as not comparable with earlier ones.

Each format has five kinds of document:

`sample`:: Small real-world-shaped files in
link:{src}/bench/corpus/samples[`bench/corpus/samples/`]: a CSV order export,
this repository's fuzz workflow (YAML), a design-tool-style SVG, a CycloneDX
1.6 software bill of materials (JSON), this repository's README, and an HTTP
browser request and JSON API response (kept in `HTTP_SAMPLES` so their CRLFs
survive). They are frozen copies; do not update them.
`small`, `medium`, `large`:: Generated documents of about 4 KiB, 64 KiB and
1 MiB in the shape of typical data: CSV rows with quoted fields and embedded
newlines, YAML service configuration with flow collections and block
scalars, an XML catalogue with attributes and entities, a CycloneDX-style
JSON bill of materials whose components carry licences, nested properties,
integers beyond 64 bits, long decimals and escaped or non-ASCII strings, a
Markdown document with headings, lists, code, quotes and tables, and HTTP
`POST` requests with a JSON body and chunked HTML responses.
`pathological`:: Inputs that stress one mechanism: very wide CSV rows and
long runs of escaped quotes, YAML nesting at the 100-level limit and long
flow sequences, deeply nested XML and thousands of attributes, JSON arrays
nested to the 128-level limit, a 200,000-number array, objects with 20,000
keys or 20,000 empty-array members, strings full of escapes or surrogate
pairs and a 100,000-digit number, unclosed Markdown emphasis and nested
brackets, and HTTP messages with many headers or thousands of one-byte
chunks. Several of these were super-linear before the fuzzing work described
in <<performance-complexity>>.

The corpus and a `manifest.json` with every document's size and hash are
written to `.roc-parser-tmp/bench/<label>/corpus/`, so you can feed a
document to a driver by hand:

[source,console]
----
$ .roc-parser-tmp/bench/full/bin/roc-yaml 100 < .roc-parser-tmp/bench/full/corpus/yaml/generated-medium.yaml
----

== Roc drivers

link:{src}/bench/roc[`bench/roc/`] holds one driver per format, each a few
lines calling the format's public entry point: `CSV.parse_str`, `Yaml.parse_str`, `Xml.parse_str`,
`JsonValue.parse_str`, `Markdown.parse_str`, and `HTTP.Request.parse_bytes` or
`HTTP.Response.parse_bytes`, each with explicit props. The timing loop is shared in
`bench/roc/Bench.roc`. The harness builds each driver with
`roc build --opt=speed`; never benchmark `roc dev` or an unoptimised build,
which is many times slower.

When an entry point is renamed, only the call in that format's driver (and the
matching line in `alloc.roc`) changes.

[cols="1,2,3",options="header"]
|===
|Language |Where |Libraries, pinned by

|Rust

|Go
|`bench/compare/go/`

|Python
|`scripts/bench_python.py` and `bench/compare/python/requirements.txt`
|csv, PyYAML (pure Python and libyaml), xml.etree, json, markdown-it-py and

program is under `scripts/` because repository policy keeps every Python file

`~/.cache/roc-parser/bench-venv` (outside the checkout, for the same reason);
pass `--python` to use another interpreter.
|===

Each program builds the same kind of in-memory structure as roc-parser:

* *CSV:* every field copied into an owned string, rows into lists.
* *YAML:* the library's generic value tree, walked once.
* *XML:* a tree of elements, attributes and text. roxmltree and
  ElementTree build one; for quick-xml and encoding/xml, which are streaming
  tokenizers, the program builds an owned tree from the events.
* *JSON:* the library's generic value tree, walked once. serde_json is
  built with `preserve_order` and `arbitrary_precision`, so like `JsonValue`
  it keeps member order and every digit of a number (it does rewrite an
  exponent such as `1E5` as `1e+5`). It is also built with `unbounded_depth`,
  because its own limit stops one level short of the 128-level document.
  encoding/json decodes into
  `interface{}` with `UseNumber`, which keeps number text but puts members in
  unordered maps. Python's `json.loads` converts numbers to `int` and `float`;
  the program lifts CPython's 4,300-digit limit on integer conversion so the
  100,000-digit number is measured. None of them rejects a repeated key: the
  last value wins.
* *Markdown:* comrak and goldmark build an AST. pulldown-cmark and
  markdown-it-py produce a flat event or token list, which is collected and,
  for pulldown-cmark, copied into owned events.
* *HTTP:* the request line or status line, headers and the body, decoded
  from `Content-Length` or chunked framing and copied. httparse only parses
  the head, so the program frames the body itself with httparse's chunk-size
  parser.

These choices, and where they still differ, are listed in
<<performance-fairness>>. Read them before quoting a ratio.

To add a comparator, add a function to the language's program, register its
name in `COMPARATORS` in `scripts/bench.py` with a one-line description of what
it measures, pin the library, and run `--quick --langs <lang>` to check that it
accepts the samples.

== Add a benchmark

* *A document:* add a generator branch or a pathological entry in
  `scripts/bench.py`, or a frozen file to `bench/corpus/samples/` with a
  licence that allows it, noted in that folder's README. Keep generated
  documents deterministic: draw randomness only from the `rng` passed in.
* *A format:* add `bench/roc/<format>.roc` calling the public entry point
  through `Bench.run!`, a branch in `alloc.roc`, a generator and samples, and
  at least one comparator per language.

`scripts/tests/test_bench.py` checks that the corpus is deterministic, that
every format has every kind of document, and that each format has a driver
and comparators; run it with `python3 -m unittest discover -s scripts/tests`.

== Read a report

Each run writes three things to `.roc-parser-tmp/bench/<label>/`:

`results.json`:: Metadata (date, machine and CPU, OS, Roc, Go, Rust and
Python versions, every crate, module and package version, the commit and
whether the tree was dirty, the corpus manifest with hashes, and what each
implementation measures), one record per document and implementation, and
the comparison table.
`report.md`:: The same as Markdown tables.
`logs/`:: Build output and allocation diagnostics.

The *comparison* table gives, per format and library, the geometric mean over
the non-pathological documents that both implementations accepted of the
ratio of median times. "roc-parser is 3x slower" means the library parsed
those documents three times as fast. Pathological documents are left out of
the mean because they measure worst cases, which differ by design between
parsers; read them individually.

In the per-document table, check these before trusting a number:

* *Result:* `rejected` means the implementation refused the document (for
  example ElementTree's nesting limit, or a strictness difference). A
  rejection is often much faster than a parse, so the times are not
  comparable.
* *Spread:* above about 10%, the machine was busy or the batch too short;
  rerun on an idle machine or raise `--target-ms`.
* *Corpus hashes and versions:* two reports can be compared only when their
  corpus hashes match and only the variable under test changed.

== Continuous integration

Cross-language performance and correctness comparisons are local-only. CI,
nightly compatibility checks and releases do not build or run the references.

Every pull request runs `--quick --langs roc --fail-on-error` as the `bench`
section of `blueprint run check` (see <<contributing>>). It fails only when a
Roc driver does not build, crashes, or exceeds its 60-second batch limit, which
catches a parser that has turned quadratic without gating on noisy timings.

== Reproducible environment with Blueprint

link:{src}/Blueprint.roc[`Blueprint.roc`] at the repository root describes the
`bench` environment for
https://github.com/lukewilliamboswell/roc-blueprint[roc-blueprint] 0.13.0: Go,
Rust (cargo and rustc), Python and Git from Nix, at the nixpkgs revision the
committed `Blueprint.lock` records, and Roc from your machine. It declares
`x86_64-linux` and `aarch64-darwin` (Apple silicon Macs), and needs Nix
with flakes enabled. Install the `blueprint` binary as <<contributing>>
describes, put the latest Roc nightly on `PATH` as `roc`, and run:

[source,console]
----
$ blueprint run bench-quick              # small corpus
$ blueprint run bench                    # full comparison, with --allocations
$ blueprint run bench -- --only csv      # extra arguments go to scripts/bench.py
$ blueprint shell bench                  # every toolchain on PATH
$ blueprint update                       # refresh Blueprint.lock
----

The first run downloads the toolchains; later runs start in a few seconds.
Generated files go to `.blueprint/`, which is not committed. Leave `ROC` unset
when you run `blueprint`: Blueprint reads `ROC` to choose the compiler that
evaluates `Blueprint.roc` itself.

*Compiler.* Roc is not pinned. The local tasks use `roc` from your `PATH`; the
report names the compiler measured. Use the latest nightly to match package CI.

Go, Rust and Python follow the nixpkgs revision in `Blueprint.lock`. Library
versions are pinned by `Cargo.lock`, `go.sum` and `requirements.txt` as above,
so a Blueprint run and a plain run measure the same library code. The Python
packages go into one virtual environment per interpreter, under
`~/.cache/roc-parser/`.

*Provenance.* The `bench` and `bench-quick` tasks pass `--blueprint` to
`scripts/bench.py`. The report's `Environment` line, and
`metadata.environment` in `results.json`, then record the SHA-256 of
`Blueprint.lock` and the nixpkgs revision it pins; a run without the flag says
`outside blueprint`. Both record the path of each toolchain, so you can check
that it came from `/nix/store`.

Without Nix, install the toolchains yourself and run `scripts/bench.py` as
shown in <<benchmarks>>; the report records every version either way.

== Profile one workload

For a closer look at one parser, build its driver with debug information and
sample it. On macOS, https://github.com/mstange/samply[samply] works on the
optimised binaries:

[source,console]
----
$ "$ROC" build --opt=speed --debug bench/roc/yaml.roc --output=.roc-parser-tmp/yaml-prof
$ samply record .roc-parser-tmp/yaml-prof 1000 < .roc-parser-tmp/bench/full/corpus/yaml/generated-medium.yaml
----

Some Roc functions keep hashed linker names even with `--debug`; `nm -n` maps
recorded offsets back to symbols.

`scripts/bench_yaml.py` is an older, YAML-only harness kept for comparing two
revisions of the YAML parser with `--replace-dep`
(`--parser-root <checkout>/package`) on the YAML microbenchmark fixtures, and
for its allocation counter, `fuzz/yaml-alloc.roc`. Its reports go to
`.roc-parser-tmp/yaml-bench/<label>/`.

[#markup-runtime-comparison]
== Markup runtime comparison

Compare HTML, SVG and MathML runtime parsing against the pinned Rust, Go and
Python DOM libraries with `scripts/compare_markup_performance.py`. Install
Python with venv support, Cargo and Go, and use a Roc compiler built in
`ReleaseFast` mode. Preparation installs the hash-pinned Python dependencies
and builds the drivers; measurement runs separately:

[source,sh]
----
python3 scripts/compare_markup_performance.py \
  --roc /path/to/roc --compiler-build-mode ReleaseFast prepare
python3 scripts/compare_markup_performance.py run
----

These are local runs. Reports and dependency caches stay under
`.roc-parser-tmp/markup/dom-compare/`; pass `--work` before each subcommand to
use another directory. Keep sources unchanged between preparation and timing:
the harness checks source and binary hashes and retains the compiler identity,
dependency locks, inputs, canonical trees and every sample.

The full comparison covers 16 geometric and document inputs. Every adapter must
first agree with an independent complete-tree model on namespace URI, local
names, attributes, exact text and child order. The projection consistently omits
namespace declarations, comments, processing instructions and doctype metadata.
Seven warmed samples use shuffled
implementation order. Parsing, DOM allocation, consumption and ordinary result
destruction or collection are timed; compilation, startup, imports, input reads
and decoding precede the timer. Roc applications use `--opt=speed --debug`.

`results.json` records `bytes_per_second`; divide by 1,000,000 for MB/s. Higher
throughput is better. The default gate requires the full Roc parser's median
elapsed time to be at most 1.5 times the fastest eligible reference on every
input; use `run --threshold 1.0` to require parity. A failing gate returns a
nonzero exit and retains the results. The full Roc lane includes source tracking
and authoring validation; the raw lane is diagnostic and does not replace it.
Compilation and checked-literal costs from `scripts/bench_markup.py` are separate
measurements.

== Roc syntax reference runtime comparison

Run `scripts/compare_roc_syntax_performance.py` locally to compare the pure Roc
parser with the pinned compiler parser on each identical input. Build the oracle
with `scripts/roc_syntax/build_oracle.py --optimize ReleaseFast` first, then pass
its executable through `--oracle-command` and the ordinary Roc syntax correctness
worker through `--probe-command`. The comparison builds its own Roc driver using
`--opt=speed`; `--candidate-binary` explicitly reuses an existing optimized driver
and marks its build provenance unverified in the report.

[source,sh]
----
python3 scripts/compare_roc_syntax_performance.py \
  --roc /path/to/roc \
  --probe-command '/path/to/roc scripts/roc_syntax/probe.roc' \
  --oracle-command .roc-parser-tmp/syntax-oracle/install/bin/roc-syntax-oracle
----

The default local run covers 33 geometric and document inputs. Repeat
`--fixtures path.json` to include selected curated or extracted corpora, retaining
each mode. Every input must first agree on acceptance and complete consumption;
accepted inputs must also agree on their normalized tree. The oracle bounds
its projection depth at 256; documented depth cutoffs match the corresponding
candidate subtree and are counted explicitly in the report. Those inputs are
labelled `partial_depth_limited`, not complete structural validation; this
local timing eligibility rule does not relax the ordinary grammar gates. Unknown grammar
variants remain errors. Timing excludes
JSON, source encoding, startup and I/O. Each parser repeatedly tokenizes, parses,
and releases its result while observing only constant-time result counts.
Neither parser performs a full AST traversal inside this timing lane; the
existing geometric benchmark remains separate.

Batches calibrate to at least 20 milliseconds, warm up, and collect five samples.
Reports retain every sample, source hash, build receipt, median ratio and a
conservative ratio lower bound (fastest Roc sample / slowest reference sample).
A one-microsecond reference floor avoids division by zero and exaggerated tiny
input ratios. The default `--max-reference-ratio 1.5` requires runtime within 1.5 times
the optimized reference on every input. Exceeding its lower-bound ratio returns a
nonzero exit and saves the exact request and timings under `failures/` for replay.
On 19 October 2026 all 33 inputs passed the 1.5 lower-bound ratio on a loaded
host (load average about 11). Medians on that host still exceeded 1.5 for some
adjacent-statement and unclosed inputs, so compare retired instructions when the
host is busy: those families run 1.1 to 1.35 times the reference's instructions.
Use `--replay failures/<hash>-<mode>.json` to time a saved input again.

`--smoke` selects only two tiny inputs and one one-millisecond sample, checks the
protocol and correctness, and disables ratio assertions. Both smoke and full
reference comparisons are explicit local activities. Build the reference oracle with
`ReleaseFast`, also required for a full ratio comparison. Its build receipt must
match the binary hash and immutable compiler revision. The smoke permits an
explicit `ReleaseSafe` build for optional safety checks.
