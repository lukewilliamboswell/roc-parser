[#roc-syntax]
= Parsing Roc source

This chapter is for authors of highlighters and source analysis tools. `RocSyntax`
parses a growing subset of current Zig compiler syntax and returns source tokens,
a syntax tree and diagnostics. Coverage is incomplete; it is not a replacement
for compiler validation. The implementation is pure Roc; the compiler reference worker is
development tooling and is not a dependency of applications using the module.
Legacy Rust compiler syntax is outside its scope.

The current implementation includes literals, identifiers, calls, field access,
lists, tuples, unary and binary expressions, simple declarations, lambdas,
conditionals, match branches, records, blocks, imports and module headers.
Patterns and type annotations have partial coverage. Interpolated strings and
other unimplemented constructs carry explicit coverage diagnostics. Check the
source doc comment and differential corpus when depending on a specific form.

== Source locations and trees

Tokens retain half-open UTF-8 byte spans: `start` includes the first byte and
`end` points immediately after the token. Comments and whitespace remain in the
token stream, so tooling can preserve the exact source even when it is incomplete.
Keep the original source alongside the result when resolving spans.

The tree uses node indices and a separate child-index buffer. Follow a node's
child range through that buffer to visit its children; do not assume adjacent
nodes are siblings. This representation supports large inputs without allocating
a separate recursive container for every syntax construct.

Byte offsets are not character columns. An editor adapter must convert positions
to the coordinate convention requested by its client. Build a line-start index
once when converting many locations in the same source.

== Highlighting and lint rules

A highlighter can start from tokens for comments, keywords, strings, literals and
punctuation. Syntax structure adds context for declarations, calls and expressions.
Preserved tokens continue to be useful when a node is malformed or its syntax is
not yet supported.

Use `RocSyntax.tokenize_str` or `tokenize_bytes` when only lexical highlighting is
needed. They return source-backed tokens and diagnostics without constructing a
tree. `RocSyntax.highlight_category(token.kind)` maps each token to a presentation
category without allocating strings or choosing theme colors.

Lint rules can traverse the tree and report diagnostics at source spans. Grouping
and operator precedence are represented structurally. Rules that need binding or
type information must add scope analysis or use compiler information; parsing
alone does not establish that a program typechecks.

Treat recovery diagnostics and implementation coverage separately. A construct
outside the implemented grammar does not establish that the source is invalid Roc.
Check the parse status and diagnostics before applying a rule that assumes a
complete tree. Code completion and highlighting should tolerate partial results.

== Compatibility and validation

The syntax reference is compiler commit
`7f11a825fb2df7fd48edb11e8c593ffdad4fcdb5`, corresponding to
`nightly-2026-09-29-7f11a82`. The implementation compiler is pinned separately to
`nightly-2026-10-15-38e6c42` in `.roc-version`. This identifies a changing language implementation,
rather than a stable language specification. Updating the implementation compiler
and updating the syntax reference are separate maintenance decisions.

The differential corpus records individual syntax rules and their coverage.
Raw fuzzing checks source preservation and structural invariants; structured
generation checks independently constructed syntax. Performance runs use optimized
builds and measure scaling as documents grow. See
{src}/docs/research/roc-syntax.adoc[the architecture research] for the reference
selection and allocation constraints behind these choices.

== Run the feedback loop

Install the Roc nightly named in `.roc-version`, Zig 0.16.0 and Python 3.
From the repository root, run:

[source,sh]
----
ROC=/path/to/pinned/roc ZIG=/path/to/zig python3 scripts/check_roc_syntax.py
----

The command checks the package, builds the pinned compiler oracle and optimized
Roc probe, checks the live protocol, compares curated cases plus 1,000 generated
expression trees, runs both fuzz smoke campaigns and checks performance scaling.
It rebuilds candidate probes and records source and executable hashes. Its
`validation.json`, step logs, differential failures and performance results live
under `.roc-parser-tmp/roc-syntax-validation/`.

The first oracle build fetches the pinned compiler Git objects when no sibling
compiler repository is available. `--roc-source /path/to/roc` selects an existing
Git repository; its working files are ignored. Build caches stay under the
validation output directory. Compiler backend libraries are not required.

Use `--generated 10000 --fuzz-runs 10000` for a larger campaign. Add `--allocations`
to collect allocation/reallocation call counts. For performance comparisons, save
the first run's `performance.json` and pass it as `--baseline /path/to/before.json`
on a later run on the same machine and compiler. An allocation call count does
not measure bytes copied or peak memory; inspect timing growth too.

To import the larger upstream source corpus, run:

[source,sh]
----
python3 scripts/import_roc_syntax_snapshots.py --roc-source /path/to/roc
----

The importer reads the pinned commit's immutable snapshot blobs and records
source hashes, parse modes and skipped snapshot kinds. This is an exploratory
coverage corpus, including invalid and historical examples. It is not a list of
programs the current compiler promises to accept. Feed the generated fixtures to
`scripts/review_roc_syntax.py` with the built probe and oracle commands. Every
disagreement remains available for inspection; unknown projections and unsupported
syntax must not be presented as structural agreement.

For each parser improvement, add a curated case for the relevant rule, check its
normalized structure against the reference, extend the independent generator
where useful, and rerun scaling when the parser's traversal or allocation changes.
Preserve minimized fuzz failures as source fixtures so the check survives corpus
and generator changes.
