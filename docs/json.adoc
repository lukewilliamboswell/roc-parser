[#json]
= Reading JSON

This chapter shows how to read a JSON document into a value whose shape you
do not have to know in advance, walk it, report mistakes with a line and
column, choose how strict to be, and write a value back out. It is for Roc
programmers who have added `parser` to their app's dependencies and need to
handle JSON that a record type cannot describe: software bills of materials,
JSON Schema files, configuration with comments, or data that must pass
through unchanged.

By default the parser is strict: it accepts only the JSON of
https://www.rfc-editor.org/rfc/rfc8259[RFC 8259], and also rejects repeated
keys and nesting deeper than 128 levels. Options relax it for common
variants, such as comments, trailing commas and a byte order mark, and add
checks, such as size limits and I-JSON numbers. It reads complete documents
held in memory; see <<json-unsupported,what is not supported>>.

Every example on this page comes from
link:{src}/docs/examples/json-guide.roc[`docs/examples/json-guide.roc`],
which CI checks and runs, and imports `parser.JsonValue`.

[#json-builtin]
== The builtin `Json` or `JsonValue`

Roc auto-imports a builtin module named `Json`. It decodes a document
straight into a record, list or other type that you name in an annotation,
in the way <<choosing-an-approach>> describes. Use it when you know the
shape of the document and a Roc type can hold all of it.

Use `JsonValue` when a record type cannot describe the document, or would
lose part of it:

* keys that are not Roc identifiers, such as JSON-LD's `@context` or
  CycloneDX's `bom-ref`;
* arrays whose items differ in shape, such as a licence that is either an
  SPDX id or an SPDX expression;
* documents of any shape, such as JSON Schema files, or a tool that works on
  every document;
* data that must pass through unchanged: the order of members, every digit
  of a number, and a definite answer for repeated keys.

The module is called `JsonValue` because the builtin already has the name
`Json`: `import parser.Json` would leave the alias unbound. Both report
invalid input with an `InvalidJson` tag, but with different payloads: a
`Str` from the builtin and a `JsonValue.Error` record from `JsonValue`. A
function that uses `?` on both needs `map_err` on one of them, because one
error type cannot hold both.

== Parse a document and walk it

`JsonValue.parse_str` reads a whole document and returns a `JsonValue`, or
`InvalidJson` with the position of the first problem. A `JsonValue` is one
of:

[source,roc]
----
JsonValue := [
    Null,
    Bool(Bool),
    Number(Str),
    String(Str),
    Array(List(JsonValue)),
    Object(List({ key : Str, value : JsonValue })),
]
----

An `Object` keeps its members in source order. A `Number` holds the
number's text exactly as written; <<json-numbers>> explains why and how to
convert it. `JsonValue` has methods for the common lookups:

* `get(key)` is the value of the first member named `key`, `at(index)` the
  item at a zero-based index, and `get_path(path)` follows a list of keys and
  indexes, with indexes written as decimal strings such as `"0"`. Each
  returns `Err(Missing)` when there is nothing there.
* `keys()` lists an object's keys in order, and is empty for anything else.
* `as_str`, `as_bool`, `as_list` and `as_object` unwrap one variant or
  return `Err(WrongType)`. `as_i64`, `as_u64` and `as_dec` convert a number.

[#json-errors]
== Show where an error is

`InvalidJson` carries a `JsonValue.Error` record: a one-based `line` and
`column` and a message. Columns count bytes from the start of the line, and
a line ends at LF, CR or CRLF. The position is the start of the problem: the
first character of a bad number or literal, the comma before a closing
bracket, the slash of a comment, or the opening quote of a repeated key.

The second error is at column 11 although `tru` is the tenth character,

surrogate pair, with no other half. RFC 8259 leaves such escapes to the
implementation. A Roc `Str` cannot hold one, so `JsonValue` rejects it
unless you ask for U+FFFD instead (see <<json-options>>).

[#json-numbers]
== Numbers keep their text

JSON does not limit the size or precision of numbers, and parsers disagree
about what `18446744073709551616` or `0.1000000000000000055511151231257827`
means: many turn every number into a 64-bit float and lose digits.
`JsonValue` does not decide for you. A `Number` holds the text from the
input, so a number read and written back keeps every digit, its sign and
the spelling of its exponent. Convert it when you need arithmetic:

* `as_i64` and `as_u64` accept only JSON integers, without a fraction or an
  exponent: `1.0` and `1e3` are `Err(WrongType)`, and an integer outside the
  type's range is `Err(OutOfRange)`. `-0` is zero.
* `as_dec` converts any JSON number, with or without a fraction or an
  exponent, that fits a `Dec`. A number outside the `Dec` range, or one that
  needs more than 18 decimal places, is `Err(OutOfRange)`.
* For a floating-point value, pass the text to `F64.from_str`, which rounds
  it to an `F64`.

[#json-duplicates]
== Repeated keys

RFC 8259 says that the names within an object should be unique, and leaves
open what a repeated name means. Readers differ: most keep the last value,
some keep the first, and some reject the document. Two programs can then
read different data from the same file, so by default `JsonValue` rejects a
repeated key. Keys are compared after their escapes are decoded, so
`"extension"` and `"\u0065xtension"` are the same key.

The `duplicates` option chooses what a repeated key means:

`Reject`:: The default. Any repeated key is an error, reported at the
repeated key.
`CollapseIdentical`:: Keep one member when every copy has an equal value,
and report an error when the values differ. Values are compared as
`JsonValue` values: numbers by their text and objects member by member in
order, so `1` and `1.0`, or the same members in another order, differ.
`KeepFirst`:: Keep the first member and ignore later copies.
`KeepLast`:: Keep the first member's position with the last copy's value, as
JavaScript's `JSON.parse` and Python's `json.loads` do.

`CollapseIdentical` reads it and would still report a copy with a different
value. The conformance review reads the pinned schema this way (see

[#json-options]
== Choose how strict to be

`JsonValue.parse_with(text, options)` takes a `JsonValue.Options` record
whose fields all have defaults, so you pass only the fields you change.
`parse_str(text)` is `parse_with(text, {})`: strict RFC 8259, no repeated
keys, and at most 128 levels of nesting. A limit or check that fails is
reported as an `InvalidJson` error at the offending value, like any other
error.

[cols="1,1,3",options="header"]
|===
|Field |Default |Effect

3+|*Limits*

|`max_depth`
|`128`
|The most arrays and objects nested inside each other. A document that is
a single number or string has depth 0.

|`max_items`
|no limit
|The most items in one array or members in one object, counted as written,
before repeated keys are handled.

|`max_string_bytes`
|no limit
|The most UTF-8 bytes in one string or key, after its escapes are decoded.

|`max_number_digits`
|no limit
|The most characters in one number, counting the sign, the decimal point and
the exponent.

3+|*Relaxations*

|`comments`
|`False`
|Accept `//` line comments and `/* */` block comments wherever whitespace
may appear. Comments are not kept.

|`trailing_commas`
|`False`
|Accept a comma after the last item of an array or the last member of an
object.

|`bom`
|`False`
|Skip a byte order mark (U+FEFF) at the very start of the document.

|`non_finite`
|`False`
|Accept `NaN`, `Infinity` and `-Infinity`, kept as `Number` text.

|`control_characters`
|`False`
|Accept unescaped characters U+0000 to U+001F, such as a tab, inside strings
and keys.

|`lone_surrogates`
|`Reject`
|With `Replace`, a `\u` escape for half of a surrogate pair becomes U+FFFD
instead of an error. A complete pair is always decoded.

3+|*Checks*

|`duplicates`
|`Reject`
|What a repeated key means; see <<json-duplicates>>.

|`top_level`
|`Any`
|`ObjectOrArray` or `Object` requires the document to be that shape.

|`interoperable_numbers`
|`False`
|Refuse numbers that an IEEE 754 double cannot hold, as I-JSON
(https://www.rfc-editor.org/rfc/rfc7493[RFC 7493]) requires: integers beyond
±(2^53^−1), more than 17 significant digits, and values that overflow or
that underflow to zero.
|===

The parser keeps its nesting on an explicit stack, so a higher `max_depth`
cannot overflow the call stack while parsing. Other operations do recurse
over a value: comparing values with `==` or `CollapseIdentical`, hashing,
and `Str.inspect`. The writer refuses more than 128 levels. Raise the limit
only as far as your documents need.

[#json-write]
== Write JSON

`JsonValue.to_str` writes a value as compact JSON, and
`JsonValue.to_str_with` takes `JsonValue.WriteOptions`:

* `indent` greater than zero puts each item and member on its own line,
  indented by that many spaces per level, with a space after each `:`. Empty
  arrays and objects are written `[]` and `{}`.
* `sort_keys: True` writes the members of every object in the byte order of
  their keys, which is Unicode code point order. Otherwise members keep their
  order.

Numbers are written as their text. In strings, only the quote, the backslash
and control characters are escaped: `\b`, `\f`, `\n`, `\r` and `\t` for
those characters and `\u00XX` (lowercase) for the rest. Other characters,
including `/` and non-ASCII text, are written as they are. The output is
byte for byte what Python's
`json.dumps(value, ensure_ascii=False, sort_keys=..., indent=...)` writes, with
the separators `(",", ":")` when compact and `(",", ": ")` when indented, for
the same number text; the conformance review checks this.

A value built in your code can hold something that JSON cannot express, and
the writer refuses it rather than write text that would read back as
something else:

`InvalidNumber(text)`:: A `Number` whose text is not a JSON number, such as
`0x10`, `+1`, `1.` or text with spaces around it, including `NaN` and
`Infinity`.
`DuplicateKey(key)`:: A key repeated in one object.
`TooDeep`:: More than 128 levels of nesting.

So what the writer returns always reads back with `parse_str` as the value
you wrote, or, with `sort_keys`, as its sorted copy. It does not keep the
input's layout: comments, whitespace and the spelling of escapes are gone,
so `"\u00e9"` is written `"é"`.

strings too, so write each backslash of a JSON escape twice: JSON's
`\u00e9` is `\\u00e9`, and `\n` is `\\n`. A single `\u00e9` is a compiler
error, because Roc's own escape is written `\u(E9)`; a single `\n` puts a
real line break inside the JSON string, which strict JSON rejects.

[#json-unsupported]
== What is not supported

These limits are by design:

Streaming:: The parser reads a complete document held in memory and returns
a tree; there is no event or token interface. Numbers, and strings without
escapes, share the input's memory instead of being copied, so a value keeps
the whole input alive while any part of it is in use.
JSON5:: Only the relaxations listed in <<json-options>> are available.
Single-quoted strings, unquoted keys, hexadecimal numbers, leading or
trailing decimal points, a leading `+`, and line breaks escaped inside
strings are always errors.
Type-directed decoding:: There is no `JsonValue.decode` or `validate_as`.
To decode JSON into your own record type, use the builtin `Json`.
Other encodings:: The input is UTF-8. `JsonValue.parser`, which takes bytes,
rejects a value that contains bytes that are not UTF-8. Convert UTF-16 and
UTF-32 documents first.
Queries and schemas:: `get_path` takes a list of keys and indexes, not a JSON
Pointer string, and there is no JSONPath or JSON Schema validation.
Preserved layout:: Comments, whitespace and the spelling of escapes are
dropped, and the writer has no option to escape non-ASCII text.

For the full module interface, see the
link:{api}JsonValue[JsonValue API reference].

[#json-performance]
== Performance

The parser scans the input bytes once, keeping its nesting on an explicit
stack as the XML parser does, so deep nesting cannot overflow the call stack.
Repeated keys are found by comparing keys in objects of up to 16 members and
with a hash table in larger ones. The module's tests parse an object with
20,000 members and an array of 100,000 numbers, and the fuzz targets run with
a time limit per input, to catch quadratic behaviour. Number text, and
strings without escapes, are slices of the input string rather than copies.
The benchmark harness compares `JsonValue.parse_str` with serde_json, Go's
`encoding/json` and Python's `json`; see <<benchmarks>> and
<<performance-fairness>>.
