[#compatibility]
= Compatibility
:idprefix: _
:idseparator: _

This chapter is for readers choosing a release, upgrading, or matching a Roc
compiler to the package. It states which compiler each release is built
for, what a version number promises, where the package runs, and what changed
in 2.0.0.

== Roc compiler

Roc has no stable release yet, and its compiler changes the language and
standard library often. roc-parser follows the latest nightly rather than
pinning one:

* Every change to `main` is tested with the latest Roc nightly of the day: the
  package, its tests, the examples, the property tests, the conformance
  reviews and the benchmarks.
* Each release is built and tested with the latest nightly of its release day,
  and its notes name that compiler under "Compilers".
* Every day, the latest release's published examples are checked, built and
  run with the latest nightly, so a compiler change that breaks the release is
  found and fixed with a patch release. This starts with the first release
  after 2.0.0, which is the first to publish what its examples print.

Use the latest nightly with the latest release. If a newer nightly breaks a
release you depend on, the nightly its notes name under "Compilers" is known to
work; the release notes also say when a migration changed the package's API.

[source,sh]
----
roc version
----

== Version numbers

Releases follow https://semver.org/[semantic versioning]:

* A patch release (such as 1.0.2) fixes bugs without changing the API.
* A minor release (such as 1.2.0) adds API without removing or changing it.
* A major release (such as 2.0.0) may remove or change API, or change what an
  existing function accepts or returns.

For a parser, which inputs it accepts and the values it produces matter as
much as its type signatures. Read the release notes for behaviour changes
even when the API is unchanged.

Roc packages are fetched by URL, so a release is a bundle URL whose name is
the hash of its content. Copy it from the {repo}/releases[GitHub releases page];
each release also publishes an SBOM and signed provenance.

== Platforms

The package is plain Roc with no platform-specific code: it does no input or
output, so it works with any Roc platform, on any system where that platform
and the Roc compiler run. CI builds and tests it on Linux x86-64, and the
conformance results in <<conformance,Conformance>> were measured on macOS with
Apple silicon.

|https://github.com/roc-lang/unicode[roc-lang/unicode] |4.3.3 |Unicode case folding, general categories and scalar handling in the Markdown module

`package/main.roc` names its release URL. Roc fetches it when it fetches
roc-parser, so applications need not add it themselves.

== The builtin `Json` module

Roc auto-imports a builtin module named `Json`, which decodes JSON into
records. roc-parser's JSON module is therefore named `JsonValue`: an
`import parser.Json` would leave the alias unbound. For the same reason its
errors use the tag `InvalidJsonValue`: the builtin reports invalid input as
`InvalidJson` with a `Str`, and keeping the tags apart lets one function pass
errors from both on with `?` (see <<json-builtin>>).

[#_changes_in_2_0_0_at_a_glance]
== Upgrading older releases

The {src}/docs/releases/2.0.0.adoc[2.0.0 upgrade guide] maps the names used by
1.x clients to the redesigned format modules. For changes since 5.0.0, use the
{src}/docs/releases/6.0.0.adoc[6.0.0 migration notes], including typed parser
problems, primitive factories and the shared streaming API.
