[#performance]
= Performance
:idprefix: _
:idseparator: _

Use this chapter to assess memory, bound untrusted input and choose what to
measure. Throughput depends on the compiler, document shape and result your
application needs. See <<benchmarks>> for reproducible comparisons.

[#performance-summary]
== Summary

Measure the package release and compiler you will deploy, using representative
inputs and increasing sizes. Keep elapsed time, allocation traffic and resident
memory separate. Benchmark reports record their source and toolchain identities;
old measurements do not establish the performance of a current nightly.

[#performance-fit]
== Choose an appropriate workload

roc-parser is a pure-Roc package that returns typed values and structured errors.
Every parser needs the complete input in memory. It has no streaming or event
interface, so measure carefully when parsing is a high-volume bottleneck or
inputs approach your application's memory limit.

A parser returning a full tree does different work from a tokenizer returning
borrowed events. Compare the representation and validation your caller actually
needs, rather than selecting a library from a single throughput ratio.

[#performance-complexity]
== Bound work on untrusted input

The format parsers use byte scanners, explicit state and bounded nesting.
Per-input deadlines in the <<property-testing,property tests>> detect excessive
work; a bounded search does not prove a complexity bound for every input.

* YAML rejects nesting deeper than 100 levels across block and flow collections.
  Nested flow collections can rescan their contents, so depth matters as well as
  byte length.
* XML uses an explicit element stack rather than native call-stack recursion.
* HTML, SVG and MathML expose source, depth, element/node, attribute, diagnostic,
  slot and progress limits. HTML recovery has a proportional work budget. Markup
  campaigns and scaling benchmarks run locally; see xref:markup.adoc#markup[web markup].
* JSON uses an explicit stack and rejects nesting deeper than 128 levels by
  default. `JsonValue.Options` also limits items, string bytes and number length.
  Large objects use a hash table to detect repeated keys.
* HTTP rejects ambiguous message framing; see <<http>>.
* CSV and Markdown scan bytes with explicit state. Test deeply nested Markdown
  containers, long whitespace runs and unmatched delimiters when changing them.

Recursive custom combinators still use the call stack. Impose a nesting limit
for untrusted recursive formats and test the limit and the first rejected input.

[#performance-memory]
== Memory behaviour

The complete input and parsed values contribute to peak memory. Allocation
traffic also depends on how many fields, nodes and decoded strings are created;
byte length alone does not describe the workload.

Text without escapes can share the input: XML text and attributes, YAML scalars
and keys, JSON strings and number text, and HTTP field values use slices where
possible. Rewritten escapes, entities and block scalars need new bytes. A
`Content-Length` body shares input memory; a chunked body is assembled.

A small retained slice can keep a large input alive. Copy values deliberately
when the caller must release the original document. Measure retained memory
separately from cumulative requested bytes and process RSS.

[#performance-fairness]
== Compare equivalent work

Benchmark drivers read input before the timed loop, consume the result and
record failures. Review their source when comparing libraries:

* A tree builder, tokenizer and borrowed-event reader return different results.
* Parsers differ in accepted syntax, duplicate-key policy and validation.
* JSON libraries differ in member ordering and preservation of number spelling.
* Typed scalar decoding adds work beyond splitting raw CSV fields.
* UTF-8 validation, copying and ownership must use equivalent boundaries.
* Runtime startup and memory overhead need a separate measurement from steady
  parsing. Python modules may delegate parsing to native libraries.

Count only inputs accepted under the comparison's declared policy. Report
rejections and resource limits separately from successful timings.

[#performance-why]
== Costs to measure

Building an owned result tree allocates and later frees lists, strings and
records. Sharing introduces reference-count work. Repeated conversion or
reconstruction of text can add copies even when the parser's scanner is linear.

Profile the deployed compiler and backend before naming a cause. Keep a minimal
control that distinguishes scanning, decoding and result construction. Changes
to compiler ownership analysis can alter allocation costs without changing the
high-level Roc source.

[#performance-simd]
== Byte scanning and slices

`Utf8.ByteClass` describes a set of bytes. `Utf8.find_any`, `Utf8.skip_class`,
`Utf8.find_line_end` and `Utf8.span_class` examine runs with `U8x16`, then handle
remaining bytes with a scalar loop. Build reusable classes outside hot loops.
The gain depends on the distance between matches and the amount of result
construction after each match.

The parsers track byte offsets and return slices where possible. Converting
bytes with `Str.from_utf8` validates UTF-8; XML can instead cut names and text
from an already validated string with boundary-checked byte slices. Sharing
avoids copies but retains the original allocation while a slice is reachable.

[#performance-tips]
== Tips for your own parsers

* Build with `--opt=speed` before measuring production throughput.
* Prefer run scanners such as `Parser.chomp_while`, `Parser.chomp_until` and
  `Utf8.ByteClass` to one combinator call and append per byte.
* Keep backtracking shallow. `Parser.one_of` and `Parser.alt` retry from the same
  position; dispatch on a leading keyword or punctuation when practical.
* Build error messages on the failure path, rather than rebuilding them inside
  successful loops.
* Avoid converting literals to byte lists or rebuilding lookup lists in a loop.
* Slice complete runs and convert text once per value the caller keeps.
* Separate outer record/line scanning from combinators for smaller pieces; see
  <<choosing-an-approach>>.
* Measure increasing sizes and adversarial orders. Time or requested bytes that
  grow faster than the input need investigation even if allocation counts look
  linear. The drivers in `bench/roc/` provide reproducible starting points.
